## T3 — Store bridge closed named-operation boundary (#19)

### 1. Decision

Граница остаётся у существующего владельца #19: `eliot-store-api` задаёт store-neutral контракт, `eliotd` выполняет semantic admission, Kernel проверяет и staging-ит неизменяемое решение, а bridge исполняет только разрешённую именованную транзакцию; новый Store Governor, универсальный backend или второй каталог владельцев не вводятся (`docs/architecture/I01-08-exact-ownership-and-call-paths.md:5-22@b71d74c0`, `docs/architecture/I05-01-storage-boundary.md:3-28@b71d74c0`).

Единицей manifest должен быть **конкретный named operation**, а не нынешний общий профиль адаптера: операция объявляет классы перехода, допустимые scopes, точную схему параметров и максимальный эффект; публикация строится из одного versioned contract catalogue, а не из prose-списка или наличия enum-варианта (`crates/storage/AGENTS.md:67-70@b71d74c0`, `docs/architecture/I05-06-admission-and-staging.md:58-82@b71d74c0`, `docs/architecture/I05-15-canonical-contract-catalogue.md:3-29@b71d74c0`, `docs/architecture/I05-17-semantic-command-families-and-activation.md:3-19@b71d74c0`).

Manifest проверяется до ORS staging в Kernel и повторно перед выполнением в bridge; отдельная проверка `eliotd` помогает построить допустимый запрос, но не заменяет эти две границы, а неизвестная операция, лишние параметры, иной scope/class/effect или несовместимый manifest не превращаются в generic query/upsert (`docs/architecture/I05-06-admission-and-staging.md:82@b71d74c0`, `docs/architecture/I01-08-exact-ownership-and-call-paths.md:36-62@b71d74c0`, `docs/architecture/I05-17-semantic-command-families-and-activation.md:3-19@b71d74c0`).

`admission_decision_digest`, исходные revisions, operation identity и точный mutation-plan digest должны сохраняться до commit/receipt; нельзя выдавать hash заново построенного Store-плана за исходное admission-решение, а arbitrary JSON продолжает использовать уже существующий `ExactJsonBytes`, не второй payload codec (`docs/architecture/I01-08-exact-ownership-and-call-paths.md:20-22@b71d74c0`, `crates/storage/eliot-store-api/src/payload_authority.rs:3-29@b71d74c0`).

Первый исполняемый набор — имеющиеся receipt/revision/ordering reads и реально используемый write path, затем bounded canonical audit/Problem reads для Doctor, отдельный bounded self-experience read и раздельные erasure intent/owner-effect/reconciliation операции; ни один из этих consumers не получает произвольную запись или автоматическое повышение semantic status (`docs/architecture/I05-03-store-neutral-semantic-api.md:3-39@b71d74c0`, `docs/architecture/I04-08-eliot-self-scope-and-immediate-system-experience-bank.md:15-27@b71d74c0`, `docs/architecture/I05-14-retention-and-erasure.md:3-24@b71d74c0`, `docs/architecture/A12-03-one-governed-write-path.md:3-16@b71d74c0`).

Для D1 сохраняется colocated BlobStore capability внутри `eliot-store-surreal`, но **единственный владелец — BlobStore, а не DB adapter**: тот же публичный контракт, один активный root, отдельные ограничения ресурсов, residency-domain identity и полноценный live set; создание отдельного `eliot-blob.exe` сейчас не требуется (`docs/architecture/I01-02-required-processes-of-the-first-complete-runtime.md:86-100@b71d74c0`, `docs/architecture/I05-12-blob-store.md:3-39@b71d74c0`).

`surreal.exe` переносится из дочернего процесса transport/bridge в Host-managed immutable dependency generation со своим Job Object и Host journal; bridge сохраняет credential-bearing соединения и semantic readiness, но не получает lifecycle/DB-root authority (`docs/architecture/I01-02-required-processes-of-the-first-complete-runtime.md:101-103@b71d74c0`, `docs/architecture/I01-09-three-registries-three-owners.md:53-75@b71d74c0`, `docs/architecture/I05-09-surrealdb-implementation.md:49-65@b71d74c0`).

Документы **не выбирают конкретный IDL-файл, executable генератора, JSON-schema dialect или новые wire-имена consumer operations**: ниже они отделены как предложения реализации, а не новые нормативные требования; отсутствующие owner-approved schemas/effect mappings нельзя заполнять догадками или объявлением всего каталога поддержанным (`docs/architecture/I05-15-canonical-contract-catalogue.md:3-29@b71d74c0`, `docs/architecture/I05-17-semantic-command-families-and-activation.md:3-19@b71d74c0`).

### 3. Current code reality

**Manifest уже существует, но не закрывает #19.** `NamedOperationManifest` явно описан как одна entry; поля на pin — name/version/classes/effect/byte limits/timeout/digest, без scope declaration и parameter schema. `default_manifest()` в adapter агрегирует все пять классов в один adapter manifest с `ReversibleMutation`, 1 MiB input/output и 30 s timeout. Это текущие literals, не утверждённые per-operation defaults. `new_with_manifest` проверяет валидность переданного manifest, но само по себе это не доказывает его происхождение из admitted catalogue (`crates/storage/eliot-store-api/src/lib.rs:906-960@b71d74c0`, `crates/storage/eliot-store-surreal-adapter/src/lib.rs:95-132@b71d74c0`, `crates/storage/eliot-store-surreal-adapter/src/lib.rs:315-335@b71d74c0`).

`NamedReadRequest` и `NamedMutationRequest` используют `BTreeMap<String, Value>`. Закрытые enum существуют, однако adapter реально обслуживает только `GetRevisionHeads`, `GetOrderingHeads`, `GetScopeRevisionView`, `ResolveWriteReceipt`; остальные branches возвращают `NamedOperationUnavailable`. Перед named read читаются все revision heads; это не реализация объявленных consistency modes для любого будущего consumer (`crates/storage/eliot-store-api/src/lib.rs:550-660@b71d74c0`, `crates/storage/eliot-store-surreal-adapter/src/apply/read_boundary.rs:195-261@b71d74c0`).

`PreparedTransition` уже есть в Store API; не создавать ещё один под #19. Его текущие поля/validation и `validate_against_manifest` нужно согласовать с T1: проверка manifest digest/class/effect не равна проверке всех I1.8 identity fields. В частности, нельзя подменять admission/mutation-plan identity результатами `plan_apply` или receipt-artifact hashing. Сохранить полезное детерминированное physical lowering, но только внутри доказанной границы исходного плана (`crates/storage/eliot-store-api/src/lib.rs:1020-1135@b71d74c0`, `crates/storage/eliot-store-api/src/lib.rs:1550-1680@b71d74c0`, `crates/storage/eliot-store-surreal-adapter/src/plan.rs:60-102@b71d74c0`).

Adapter уже имеет `plan_apply_with_payload_authority` и проверку соответствия authorities параметрам. При этом legacy `plan_apply` передаёт `None` для всех authorities: наличие новой функции не доказывает, что production ingress использует её для каждого authority-bearing payload (`crates/storage/eliot-store-api/src/payload_authority.rs:3-29@b71d74c0`, `crates/storage/eliot-store-api/src/payload_authority.rs:136-188@b71d74c0`, `crates/storage/eliot-store-surreal-adapter/src/plan.rs:60-102@b71d74c0`, `crates/storage/eliot-store-surreal-adapter/src/plan.rs:184-223@b71d74c0`).

C1/C2 должны убрать универсальное правило там, где owner-approved payload schema допускает JSON null: explicit null, absent, false и zero не взаимозаменяемы. #### 1. T3-C1 — Generated per-operation manifest и настоящий parameter validation

**Owner:** #19. **Depends on:** none; согласование contract wave с #18/#13. **Owned paths:** `crates/storage/eliot-store-api/src/lib.rs`, новые `src/operation_catalogue.rs`, `src/operation_parameters.rs`, `examples/emit_operation_manifest.rs` в том же crate; его `Cargo.toml` при необходимости. Это один writer всей public Store schema, не отдельный каталог в Governor/bridge.

**Формат и генератор — конкретное предложение реализации.** Одна Rust declaration table/macro в `operation_catalogue.rs` генерирует enum/descriptor membership и typed parameter-schema associations; example `emit_operation_manifest` сериализует тот же набор в canonical JSON через существующий `canonical_json_bytes`. `schemars` уже используется Store API. Не создавать параллельные редактируемые YAML, JSON и Rust списки. Команда после реализации: `cargo run -p eliot-store-api --example emit_operation_manifest`; запуск здесь не выполнялся. Если owner #13 уже принимает другой общий IDL producer, он заменяет именно этот producer, а не добавляет второй.

Сохранять `NamedOperationManifest` как **одну entry**, расширив её operation identity/kind, owning-section reference, exact schema revision/digest, scope declaration, compatibility и bounds. Typed read entry имеет effect `Read`, но не притворяется `CaptureCandidate`; требование непустого transition-class set относится к mutations. Entries хешируются без собственного digest, set digest — по упорядоченным entry identities/digests и их contract/schema/profile bindings. Не сортировать сами команды PreparedTransition. Одинаковые inputs дают одинаковые bytes; timestamps и mutable evidence status не входят как скрытые inputs. Схема произвольного user payload сохраняет `ExactJsonBytes`; closed validation относится к control/parameter contract, не переписыванию пользовательского JSON.

Нельзя генерировать exact parameter schema из unconstrained `BTreeMap`: сначала определить owner-approved typed parameters каждого активируемого operation. Initial active reads — четыре реально исполняемых операции из §3; остальные enum variants могут оставаться известными, но unsupported и не advertised. Аналогично исключить mutation, для которой нет доказанного handler/schema/consumer.

**Acceptance:** действующий API validation использует generated descriptors; одинаковая генерация byte-identical, unknown/extra/control-substitution parameter отклонён до dispatch. Минимум: один accepted typed request, один rejected extra field, один digest-change test. **Deferred:** весь будущий global catalogue, универсальный schema framework, новые defaults без owner input. **Unblocks:** общую зависимость всех девяти PR; непосредственно #1164/#1196 и основу остальных. **Authority:** `docs/architecture/I05-15-canonical-contract-catalogue.md:3-29@b71d74c0`, `docs/architecture/I05-17-semantic-command-families-and-activation.md:3-19@b71d74c0`, `crates/storage/eliot-store-api/src/lib.rs:906-918@b71d74c0`.

#### 2. T3-C2 — Enforce the same admitted operation до staging и commit

**Owner:** #19; Kernel leg — #15/T6, semantic transition fields — #18/T1. **Depends on:** C1, T1 exact PreparedTransition binding, Kernel-owned NamedReadCapability binding. **Owned paths:** Store API `src/lib.rs`, `src/wire.rs`, `src/store_failure.rs`; adapter `src/lib.rs`, `src/apply.rs`, `src/plan.rs`, `src/apply/{atomic_write,read_boundary,receipt_reconciliation}.rs`; bridge `src/lib.rs`, `src/request_dispatch.rs`. После C1, не одновременно с последующими Store slices. Kernel/receipt-owner files не выдаются второму T3 writer: их изменения принимает существующий owner соответствующей внешней задачи.

Перед ORS Kernel проверяет active manifest-set digest, operation membership, exact schema, operation-specific scope/effect/proofs и исходную plan identity. В bridge после authenticated frame повторяются те же ограничения перед любым provider I/O с эффектом; schema/manifest mismatch не исправляется normalization или fallback. Сопоставление query/scope/principal/daemon/expiry выполняется по Kernel-issued capability, не по строковому prefix `scope_id`. Legacy broad `default_manifest` и production use старого aggregate validator удаляются, а не остаются emergency path.

Для arbitrary JSON wire admission сохраняет raw authority до `Value`; транзакция обязательно вызывает authority-carrying path при наличии authority. Не вызывать `ExactJsonBytes::parse` на уже пересериализованном `Value`. Binding covers original admitted plan и каждый payload digest; физическое lowering не меняет semantic command/target/effect. Genesis, recovery и schema bootstrap — явно отдельные закрытые admitted paths, не wildcard-исключения для пустого списка операций.

**Public interfaces:** C1 validators встраиваются в существующие `PreparedTransition`, `StoreRequest`, `CanonicalStoreClient`; поля исходного admission/mutation-plan binding берутся из T1, без второго transition type. Сигнатура общего исполнения сохраняется:

### 6. Risks

**Catalogue bootstrap.** I5.15 определяет ownership и build receipt, но не concrete producer/IDL/dialect или exact schemas новых consumers. C1 должен рано показать небольшой generated catalogue, реально используемый validator, и перечень ещё не admitted entries. Принять предложенный Rust→canonical-JSON producer — implementation decision #19/#13; выдавать его за уже предписанный документацией запрещено. Без schema entry отклоняется конкретная операция, а не создаётся generic escape hatch. Полное global catalogue closure не требуется для первого реально исполняемого Store subset.

**T1 и T6 — один contract wave.** C1 не должен создать второй `PreparedTransition`; C2 требует исходный admission digest, plan/source-revision binding и Kernel-owned read capability. Если T1/T6 не предоставили их executable public contract, не заменять отсутствующую проверку digest строки на `true` и не объявлять Store boundary закрытой. Doctor canonical audit и ORS execution ledger должны остаться разными слоями; #1167/#1175 направляются одному #461 writer.

**T2 и Host credentials.** Перенос server lifecycle не даёт Host права выполнять SQL и не даёт bridge права снова spawn-ить provider «на случай недоступности Host». #100 предоставляет process mechanics, #14 — authority/lineage, #19 — credential-bearing protocol/readiness. Не объявлять новый SDK, RocksDB/SurrealKV profile или конкретную Surreal version qualified без compatibility receipt; текущий custom RPC и target default — отдельный integration/evidence вопрос, не повод скрыто сменить backend в T3.

**Payload compatibility.** Existing authority-carrying helper может быть обойдён legacy ingress. C2 проверяет настоящий маршрут и unchanged bytes/digest, не только helper test. Structured operation control и arbitrary user payload имеют разные правила: нельзя провести control identity через payload, но нельзя «исправлять» payload переупорядочиванием/преобразованием `Value` и сохранить старый claimed digest.

**Erasure не сводится к manifest entry.** #1130 ещё должен дать конечный target/hold/approval/effect contract. Ни typed tombstone, ни protected Blob root не доказывают физическое и derivative erasure. Неполный live set запрещает GC; исчезновение доступного payload после подтверждённого erasure — REDACTED, а не BROKEN_INTEGRITY. Отсутствие этих owner statements не является critical documentation contradiction и не даёт права придумать их в Store.

**Параллельные задачи.** T7 удаляет legacy только после реального split-path readback/recovery; T3 не оставляет скрытого fallback и не объявляет весь legacy retired. T5/T8 используют ту же canonical admission boundary и не получают raw Store access. T0 может принять первый operational subset C1–C3/H/B без ожидания всех optional consumers, но не может из этого вывести полное закрытие #1130/#461/#1199 или Product PASS. #1195 получает digest artifacts, не нового самоназначенного compiler owner; #13 получает отдельные support/evidence dimensions, не агрегированный зелёный статус.
