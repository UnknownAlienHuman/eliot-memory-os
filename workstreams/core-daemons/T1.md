## T1 — Governor ownership closure (#18)

### 1. Decision

`eliotd` is the sole semantic application owner: compose the existing `eliot-governor::GovernorComposition` and its Governor-domain owners, rather than introducing a Governor inside ControlBoard, Skill, Doctor, erasure, a worker, or the legacy executable (`docs/architecture/I01-02-required-processes-of-the-first-complete-runtime.md:47-66@b71d74c0`; `docs/architecture/I01-08-exact-ownership-and-call-paths.md:5-22@b71d74c0`).
The physical composition root remains `bins/eliotd`, where authenticated Kernel adapters are constructed and injected; semantic transitions belong in `crates/governor`, while Kernel retains identity, active authority, fencing, ORS and generation routing (`bins/AGENTS.md:49-54@b71d74c0`; `docs/architecture/I01-08-exact-ownership-and-call-paths.md:5-22@b71d74c0`).
ControlBoard receives Governor-owned access/read/command adapters and the existing Agent Coordinator projection, but its DTOs, hashes and UI role selections cannot issue authority or become another task/review store (`docs/architecture/I01-08-exact-ownership-and-call-paths.md:28-46@b71d74c0`; `docs/architecture/I11-02-controlboardview.md:3-26@b71d74c0`; `crates/surfaces/eliot-controlboard/src/swarm_read.rs:3-10@b71d74c0`).
Skill promotion, erasure admission and Doctor-result acceptance use the same Governor admission and canonical transition path; their domain crates supply meaning or evidence, not independent writers (`docs/architecture/A12-03-one-governed-write-path.md:3-16@b71d74c0`; `docs/architecture/I07-25-skill-lifecycle-interaction-and-execution-evidence.md:25-40@b71d74c0`; `docs/architecture/A13-03-module-supervision-and-doctor.md:39-55@b71d74c0`).
Governor authority decisions become effective only through the existing G-01/P-07 activation boundary and an exact Kernel activation receipt, with Kernel-first revocation and no reconstruction of rights from a numerically larger epoch (`docs/architecture/I06-10-authority-records.md:23-68@b71d74c0`; `crates/governor/eliot-authority/src/activation.rs:54-75@b71d74c0`).
Module Catalog, Generation Registry and Capability Registry remain three different responsibilities, so provider availability, a successful process start or a background-job checkpoint never substitutes for semantic admission (`docs/architecture/I01-09-three-registries-three-owners.md:3-22@b71d74c0`; `docs/architecture/I03-06-model-route-and-portfolio-policy.md:25-51@b71d74c0`).
Move still-consumed legacy behavior to those documented owners, retain only explicitly justified expiring regression compatibility, and retire the legacy authority/write/finish paths rather than transplanting their combined architecture (`crates/eliot-app/AGENTS.md:31-61@b71d74c0`; `workstreams/core-daemons/AGENTS.md:44-53@b71d74c0`; `docs/architecture/I06-11-gate-and-decision-mapping.md:50-65@b71d74c0`).
These decisions remove the missing-owner question, not the remaining implementation and runtime-proof requirements: only a proof-bearing `VERIFIED_COMPLETE` may close a task (`START.md:18-21@b71d74c0`; `docs/architecture/A10-08-verification-and-finish.md:5-21@b71d74c0`).

### 6. Risks

**Missing contract detail is not permission to invent it.** I1.8 defines the named-read capability and semantic/operational split, but the inspected daemon recovery ports do not provide a complete general-purpose G-06 named-query adapter. T3/#19 must identify the admitted shared read subset, operation/manifest binding and receipt behavior. Do not implement a fake broad `CanonicalStoreClient` with unavailable write methods to satisfy `ReadService<C>`. Likewise, I5.14/I15.14 define erasure scope/ordering but not the concrete versioned finite-closure query and per-owner child-operation packet required by #1130. Those exact contract definitions must come from that owner; T1 does not assert that a production `ErasureScopeSnapshot` constructor already exists. The result is a named #19/#1130 prerequisite, not “unknown Governor owner.” T1.3 additionally requires P-07 to demonstrate how its grant/introduction IDs, snapshot ID and `AuthorityBinding` bind the exact compiled `KernelAuthoritySnapshot` and canonical receipt. I6.10 specifies the data and saga, not permission to implement a transport that merely stamps a caller-supplied snapshot ID.

**The first slice must expose false readiness early.** Recovered owner count, a nonzero revision or a snapshot digest alone does not establish live cross-owner coherence. T1.1's changed-head and restart case is the first discriminator. Failure leaves affected reads stale/unavailable, does not erase a committed receipt, and does not turn a missing optional capability into a new Kernel failure domain. T1.2 then exposes whether the shared hash/transport contract can preserve the original exact request terms without a local fallback.

**Shared identity migration is a hard dependency.** Doctor and ControlBoard still contain scalar fence representations at the pin; Doctor's `check_fence_against_epoch` compares sequence, not full lineage identity. Neither may authorize an effect by mapping a UI digest or scalar to the current canonical epoch. T6/#64 owns that migration; T1 consumes it. The zero-model Swarm read profile also remains zero-model until its owning contract is deliberately versioned, regardless of T4/T5 execution progress.

**Cross-chat boundaries:** T0 retains the installed Product Pulse and sequencing across shared files; T2 owns the sole ProcessExecutor; T3 owns Store operations, atomicity and shared errors; T4 owns exact provider-turn/AgentAttempt binding; T5 owns claim-bound worker/adapters; T6 owns Kernel Doctor/testd/epoch mechanics; T7 owns full legacy retirement; T8 owns every Dreamer-specific contract, handler and runtime change. T1 gives them Governor ownership and admission constraints without changing their paths or claiming their proof.

**Not all seventeen PRs should be “released” together.** #1196 and #1200 still require real producer/consumer dispositions; Doctor and activation have overlapping blocker PRs; several bodies describe an older source snapshot. Queue one implementation track per owning issue and rebase each slice onto the controller's published current `main` before changing code. Preserve this document's pinned evidence instead of silently updating its citations to newer source.

**Verification ceiling:** this deliverable is an implementation decision/queue plan. No Rust compilation, repository verification scripts, Windows execution or live Store/Kernel tests were executed for it; every Rust fragment is UNCOMPILED. It changes no accepted normative shard, proves no runtime closure and does not close #18. The managers must compile the proposed interfaces and obtain the focused real edges before treating the corresponding prerequisite as implemented.
