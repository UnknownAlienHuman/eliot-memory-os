## T10 — Roll back a first install that holds a signed activation intent (#1325)

### 1. Decision

**Disposition: ownership is resolved; the pre-Host authenticated entry and the complete first-install no-return predicate are not specified by the cited contracts. This is a non-normative implementation brief, not authorization to bypass either gap.** (`docs/architecture/I03-15-installation-and-update-transaction.md:17-31@7a1a6eaa`; `docs/ARCHITECTURE_CONTRACT.md:1-28@7a1a6eaa`.)

1. Installer/bootstrap owns the installation transaction while no Host is active, but Host owns activation/recovery after establishment of its HostInstallationEpoch; stopping a service does not, by itself, prove that this lineage never existed (`docs/architecture/I03-15-installation-and-update-transaction.md:23-31@7a1a6eaa`).
2. Retirement of an existing Host activation projection must therefore remain a Host-owned transition, not a CLI deletion of `activation_projection_intent` or an installer-created substitute for Host authority (`docs/architecture/I01-09-three-registries-three-owners.md:75-94@7a1a6eaa`).
3. The existing authenticated mutation is `RedbInstallationRegistry::abort_pending_activation`, guarded by a live `HostOwnerEpochCapability` and an expected registry revision; it is a reusable mechanism, not documentary permission for the installer CLI to acquire that capability (`crates/kernel/eliot-installation/src/installation_registry.rs:873-900@7a1a6eaa`; `docs/architecture/I01-09-three-registries-three-owners.md:75-94@7a1a6eaa`).
4. None of the cited installation/update contracts selects a pre-Host recovery transport, delegates abort authority at signing, or specifies an owner-signed abort envelope, so selecting one of those alternatives as already authorized would invent a contract; ordinary demand-start permission does not fill that gap (`docs/architecture/I03-15-installation-and-update-transaction.md:23-50@7a1a6eaa`; `docs/architecture/I03-01-installation-form.md:23-27@7a1a6eaa`; `docs/architecture/I14-16-kernel-and-host-update.md:3-25@7a1a6eaa`).
5. `recover` must obtain fresh effect observations through the existing Windows provider and installation coordinator, retaining `UNKNOWN_OUTCOME/ROLLBACK_REQUIRED` when observation or identity binding remains unresolved, rather than inferring absence from a timeout, a missing PID, or transaction JSON (`docs/architecture/I03-15-installation-and-update-transaction.md:37-50@7a1a6eaa`; `crates/kernel/eliot-platform-windows/src/service_registration.rs:738-785@7a1a6eaa`).
6. The documents force refusal of fake binary rollback across irreversible format/migration changes, but explicitly preserve isolated-backup restoration or a separately proven rollback path; they do not define a complete first-install Boolean predicate equating service `Running`, credential application, Phase-B preparation, and irreversible migration (`docs/architecture/I19-11-rollback.md:3@7a1a6eaa`; `docs/architecture/I14-14-module-hot-replacement.md:39-41@7a1a6eaa`; `docs/architecture/I03-15-installation-and-update-transaction.md:17-20@7a1a6eaa`).
7. Module rollback is a new Kernel/ORS cutover with a newer epoch, not resurrection of an old epoch, and this rule must not be misused to make the installation transaction a second ModuleGeneration owner (`docs/architecture/I14-14-module-hot-replacement.md:39-41@7a1a6eaa`; `docs/architecture/I03-15-installation-and-update-transaction.md:50@7a1a6eaa`).
8. Consequently, the observation/reconciliation work below can proceed without granting new authority, while intent retirement and its CLI/Host transport remain dependent on the two explicit decisions in T10-00; this brief cannot itself become a third normative source (`docs/architecture/I03-15-installation-and-update-transaction.md:48-50@7a1a6eaa`; `docs/ARCHITECTURE_CONTRACT.md:1-28@7a1a6eaa`).

### 3. Current code reality

**Two durable stores and a missing terminal bridge.** `signed_activation.rs` first commits the transaction's activation projection intent, then attempts the registry pending projection, reconciling an exact existing pending value after response loss. There is a crash window between those commits; consequently, neither “intent exists” nor “pending is absent” proves a completed activation or a completed abort (`crates/kernel/eliot-installation/src/signed_activation.rs:520-718@7a1a6eaa`). Its bootstrap path also uses `InstallationActivationProjectionIntent`, but derives synthetic envelope/payload digests from the retained transaction without authority bytes. Presence of this shared type is not proof that a cryptographic signing or Host-epoch transition occurred (`crates/kernel/eliot-installation/src/signed_activation.rs:719-799@7a1a6eaa`). Preserve the original signed-envelope binding where present; do not replace it with bootstrap approval.

**The existing abort is usable only behind stronger eligibility checks.** `ApprovedGenerationRegistry::abort_pending_activation_unchecked` validates transaction/plan identity, accepts a matching previously aborted terminal idempotently, refuses an active/LKG generation, removes candidate approvals, and records `PendingActivationTerminalDisposition::Aborted`. It does not independently check Phase-B or service-start history (`crates/kernel/eliot-installation/src/approved_generation_registry.rs:3554-3613@7a1a6eaa`). The production public wrapper applies the live Host capability and revision-CAS checks (`crates/kernel/eliot-installation/src/installation_registry.rs:873-900@7a1a6eaa`). Do not expose `_unchecked` or its test-only wrapper as a CLI shortcut.

**The current production Host caller also needs the eventual common guard.** `HostComposition::reconcile_pending_activation` invokes `abort_pending_durable` after a first-install contour-start error when `prior_active_generation` is absent. That condition alone is not the full #1325 eligibility predicate (`bins/eliot-host/src/host_activation_durable.rs:4-50@7a1a6eaa`). `abort_pending_durable` already performs mutation followed by readback, including recovery after a lost response, but its positive readback checks revision and absence of pending/active/candidate rather than an explicitly matched abort terminal (`bins/eliot-host/src/host_activation_durable.rs:689-739@7a1a6eaa`). Harden this existing caller as well as any new entry.

**Recover currently reaches rollback too early.** CLI dispatch calls `WindowsInstallationCoordinator::rollback` directly (`bins/eliot/src/main.rs:2100-2116@7a1a6eaa`). The coordinator rejects the intent before reconciliation; an unresolved effect then causes quarantine. Normal driving also returns immediately on `Unknown`, while an expired persisted start deadline becomes another unknown before a useful late readback (`crates/kernel/eliot-installation/src/lib.rs:6732-6795@7a1a6eaa`; `crates/kernel/eliot-installation/src/lib.rs:6970-6990@7a1a6eaa`; `crates/kernel/eliot-installation/src/lib.rs:8083-8205@7a1a6eaa`). Recovery needs a readback-only path, not re-entry into normal apply.

**Keep the existing effect ownership and absence checks.** Normal service-start reconciliation binds observed process lineage to the persisted start disposition; `AlreadyRunning` is not `StartedByCaller` (`crates/kernel/eliot-installation/src/lib.rs:7840-7920@7a1a6eaa`). Rollback traverses `Applied/CreatedByTransaction` effects in reverse and verifies exact external identity before removal (`crates/kernel/eliot-installation/src/lib.rs:8196-8370@7a1a6eaa`). Current validation distinguishes ordinary filesystem/credential/package absence from service-specific observations; #1306 must not be “fixed” by admitting an empty precondition or fabricating a filesystem snapshot for SCM (`crates/kernel/eliot-installation/src/lib.rs:2790-2965@7a1a6eaa`).

**Windows already owns the physical observations.** `ServiceRegistrationInspection::Absent { proof }` carries the native proof; `ServiceRegistrationRuntimeInspection::Absent` is a bare classification, whereas `Matching` carries `ServiceRuntimeObservation` with current state and process identity (`crates/kernel/eliot-platform-windows/src/service_registration.rs:930-1119@7a1a6eaa`). Consume a real registration absence proof for destructive recovery; do not upgrade the bare runtime variant into an authenticated historical no-effect claim. A stopped service registration still exists, and a stopped process may previously have run.

**Retain neighboring fixes.** The pinned CLI drops its registry writer before the SCM start/convergence wait and uses bounded terminal-reconcile lock handling (`bins/eliot/src/main.rs:2216-2225@7a1a6eaa`; `bins/eliot/src/main.rs:2390-2420@7a1a6eaa`). Host and Watchdog registration observations already require exact service-control grant receipts (`crates/kernel/eliot-installation/src/lib.rs:2807-2850@7a1a6eaa`). Recovery must preserve these behaviors rather than reintroduce the #1329/#1339 lock problem or weaken #1345 DACL validation.

### 6. Risks

**The central uncertainty is contractual, not a Rust syntax problem.** T10-00 may reveal that the only permitted first-install recovery requires a different Host startup context, or that historical runtime authority cannot be excluded for the saved timeout transaction. Its first discriminator is the real retained Host/registry/transaction lineage, not a `Running` check performed after the fact. Do not reinterpret missing evidence as permission to delete.

**No-return has three outcomes for recovery: proven eligible, proven outside abort-to-none, and unresolved.** The cited documents do not supply the full event-to-predicate mapping. The task's narrow positive case is mandatory acceptance, not a universal formula. Current `Stopped`, absence of `Applied`, and absence of `active_generation` cannot independently establish that an irreversible effect never occurred. Conversely, a refused first-install abort is not automatically proof of irreversible migration; compatible generation switch and proven isolated recovery remain separate owner paths.

**Cross-store races and replay can invalidate an otherwise correct local change.** Registry abort, transaction retirement and OS cleanup are not one atomic transaction. The exact terminal must survive response loss and bind the original intent strongly enough to reject a concurrent activation, a different plan or replay. Retiring registry service approvals must not destroy the only retained identities needed for later cleanup. A rollback-intent/owner handoff must also prevent a normal apply/Host activation from running between observation and retirement.

**Schema and evidence are not interchangeable.** Adding a resolved-absence record must preserve old transaction decoding safely and keep it out of successful-apply predicates. SCM registration absence, absence of a Running process, and absence of filesystem roots are different facts. T10-01's first native readback regression exposes this distinction before any destructive behavior is enabled.
