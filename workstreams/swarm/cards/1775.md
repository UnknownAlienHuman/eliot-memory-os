**D1 — the effect boundary authenticates only two of five `StateFence` members.**
`crates/kernel/eliot-process/src/origin_challenge.rs::OriginControlGrant::binds_effect_currency`
takes exactly three arguments (`live_lineage_id`, `live_authority_sequence`,
`now_unix_ms`) and compares **only** `expires_at_unix_ms` and
`self.state_fence.authority_epoch` — it returns `ExpiredDispatchPermit` or
`StaleStateFence` and nothing else. `eliot_contracts::StateFence` has five
independent members (`authority_epoch`, `resource_generation`, `task_revision`,
`policy_revision`, `integration_revision`). At
`bins/eliot-kernel/src/process_execution.rs::ProcessExecutionGateway::authorize_effect_with_grant`
the grant is checked by `binds_target_for_operation` (physical identity + generation +
operation) then `binds_effect_currency`, then
`grant.installation_id() != Self::live_origin_installation_id()?`; the live epoch it
passes is read from `self.snapshot_binding.authority_epoch().current`. **No current
owner-issued `StateFence` is ever loaded at the effect boundary and
`fences_match_exact` is never called there.** A grant decided under
`policy_revision = P1` therefore still authorises `executor.cancel` after the policy
owner publishes `P2`, with epoch, generation and PID/start identity unchanged — the
full fence was authenticated at decide time but its *currency* at the privileged cut
is not proven.

**D2 — `ATTACH_CREDENTIAL_BLOCKED_ROW` is factually wrong.**
`crates/kernel/eliot-process/src/operation_owner_map.rs::ATTACH_CREDENTIAL_BLOCKED_ROW`
declares `admitted_target: "none admitted"`, `proof: "none admitted"`,
`effect_primitive: "none"`, `production_caller: "none admitted"`,
`admission: OwnerAdmission::Blocked`, and its `gap` says binding an actual connection
plus retained process identity is *"implementation work still open"*. The live path
exists: `crates/storage/eliot-store-surreal-adapter/src/client/session.rs::RpcSession::signin`
(`session.rs:97`, trait method `:392`, impl `:412`) is reached from
`client/session.rs::authenticate_provider` (`:425`) with
`request_with_guard(..., prove_connection_owner = true)` (`:170`, `:181`), which at
`session.rs:251` calls
`crates/storage/eliot-store-surreal-adapter/src/client/provider_owner.rs::ProviderOwner::validate_connected_peer`
(`:195`) → `observe_loopback_tcp_connection_peer_owner` (`:229`). This is **not** a
PID or name match: it is the connected provider socket plus `ProviderOwner`'s exact
child PID / start / image lease and data-root lease, with the effect primitive being
the exact `signin` send.

**D3 — `is_documented_production_caller` cannot fail.**
`crates/kernel/eliot-process/src/operation_owner_map.rs::is_documented_production_caller`
only `flat_map`s `row.production_caller.split("; ")` and compares each string with
**another string in the same table**. It never greps or otherwise cross-checks the
tree, so a hand-authored row can contradict reality (exactly what D2 is) and nothing
breaks. Its own doc says it is *"a registry lookup for verifiers … never an
authorization decision"* — that is true and must stay true; the missing half is the
**mechanical check** that every destructive or credential call site in the tree is
either present in the map or has an explicitly proven unsupported gate.
