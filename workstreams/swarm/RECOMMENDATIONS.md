- 543 задачи, 2422 PR (медиана 3 PR на задачу), 788 возвратов на доработку, 404 задачи доходили до CODE-COMPLETE и 267

- Главные причины, по убыванию вреда:
  1. **Работа кусками.** Задачу дробили на «пакеты», «карточки», «срезы» — каждый кусок принимался отдельно, задача
     не заканчивалась. Владелец: «Каждый Issue — самодостаточная единица».
  2. **Несколько задач в одной ветке.** PR одной задачи затаскивал недоделанный код других — возвраты за чужой код
     (#4601: 5 возвратов, все из-за чужих задач в lane/CB2; на 02.10 lane/CB держит ~20 коммитов 8 задач).
  3. **Ложное «готово».** Исполнители объявляли пункт MET без вызывающего кода, проверяющий подтверждал, а внешний аудит
     владельца возвращал (01.10: в 78 из 88 задач, которые проверяющий подтвердил).
  4. **Выдумывание вместо BLOCKED.** Проверяющий требовал контракты, которых нет в документации, линии их сочиняли,
     аудит их отвергал. Исправлено 02.10: нет контракта → BLOCKED с номером задачи-владельца или разделом документации.
  5. **Root мешал.** 8 смен правил за одну ночь, скрипты с побочными эффектами без проверки на образце, будили и
     прерывали чужие сессии. Root сам не читал задачи, по которым отдавал приказы.
  6. **Не читали задачу целиком.** В задачах и их комментариях всё расписано («для идиотов написано как и что делать»),
     а линии работали по пересказу root (TASK.md, BATCH.md).

## 2. Как организовать следующий спринт
1. **Единица = задача, одна в полёте на линию.** Одна ветка `lane/<L>`, пересоздаётся `git switch -C lane/<L>
   origin/main` перед каждой задачей; один коммит, один push, `PUSHED`. Проверять это механически, а не прозой:
   приёмка должна отказывать, если ветка содержит коммиты с номерами других задач или файлы вне путей задачи.
2. **Непересекающиеся пути.** План спринта делить по семействам путей (крейт/набор файлов), а не по номерам задач:
   две линии не должны держать один файл одновременно (02.10: W4 #1884 и CB #1888 независимо написали один и тот же
   механизм CPU rate в одном файле). Каждой задаче в плане — список файлов; пересечения решаются до старта.
3. **Сначала контракты, потом код.** Карта блоков показывает, какие отсутствующие контракты держат больше всего
   работы. Их закрывает один архитектор (сильная модель, читающая документацию) правкой документации/задачи —
   до того как линии возьмут зависимые задачи. Линии контракты не придумывают никогда.
4. **Порядок по зависимостям.** Ядро (kernel/ORS/store) раньше остального; задача-блокер раньше заблокированных.
5. **Проверка.** Линии: fmt + clippy своих крейтов, тесты написаны, но не запущены. Тесты запускает один проверяющий
   (или root) один раз на задачу. Проверяющий опровергает только с цитатой нарушенного предложения и контрпримером;
   отсутствие контракта — BLOCKED, не REFUTED.
6. **Root меньше вмешивается.** Правила меняются редко и одним пакетом; любой скрипт root — сначала на образце;
   отчёт раз в час; никаких прерываний живых сессий. Root читает задачу сам, прежде чем отдавать по ней приказ.
7. **Сшивание — отдельный план.** Связи внутри задачи — часть её поставки. Сшивание между задачами (недостижимые
   крейты, Dreamer не подключён) — отдельные задачи с владельцем и порядком, не «потом как-нибудь».

- Блокеры с наибольшим охватом (раздел «Blockers» в BLOCK-MAP.md) — первые кандидаты на «контрактный» спринт.
