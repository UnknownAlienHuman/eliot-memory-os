# ROOT-DIRECTIVE v1.5 — продукт не недописан, он не собран

**Основание:** внешняя ревизия дерева от 2026-08-26 на `d5f0fdc` + рабочий оверлей.
**Продолжает:** `ROOT-DIRECTIVE-v1.4.md`. Действующая копия программы — `docs/tasks/RECOVERY_PROGRAM_v1.md` (v1.3).
**Авторитетность:** программная. Не Architecture, не Implementation, не Product Proof, не cutover.
**Отменяет:** hosted-прогон как условие любого гейта до восстановления квоты (§6); DoD W3 в части блокирующего STU-гейта (§3.3); утверждение программы, что W4-01 блокирован W3-04 (§3.1).
**Не отменяет:** ничего из принятого в W0/W1, решение по cutover (Option A), решение по `AdmittedSwarmPlan`.

## 0. Что показала проверка

**Первое.** Из 119 отказов класса `Unimplemented` **111 — типизированный `PlanGap`**, и **64 называют блокировщик дословно**:

```
CommandAvailability::PlanGap { missing_work_id: "A-06", dependency: "eliot-mcp" }   ×21
WorkerError::PlanGap { detail: "P-03 ProcessExecutor was not injected" }
WorkerError::PlanGap { detail: "G-01-facing admission provider was not injected" }
TransportError::PlanGap { dependency: "eliot-platform-windows", reason: "…не скомпонован" }
… "durable replay provider was not injected", "verification port is missing"
```

Ключевые слова: **`was not injected`**, **`port is missing`**, **`dependency: <крейт, который существует>`**.

`eliot-mcp` — **1 894 строки** рабочего кода, ноль потребителей, блокирует 21 команду CLI. `eliot-platform-windows` — 703 КБ. `ProcessExecutor` живёт в `eliot-process`, на который ссылаются 24 манифеста.

**Продукт не недописан. Он не собран.** Реализации есть и недостижимы, потому что их никто не композирует. Отсюда же ноль вызывающих у `commit_canonical` и 40 библиотек с нулём потребителей. Продукт уже написал список работ о себе — типизированно, с указанием блокировщика. Его надо **доделать**, а не мерить термометром.

**Второе, и это блокирует всё остальное.** `cargo test --locked --workspace` на текущем дереве **красный**:

```
test result: FAILED. 323 passed; 1 failed; 2 ignored
host_runtime::supervised_process::tests::supervised_process_timeout_forces_job_and_proves_zero_orphan
```

Тот же тест изолированно проходит 3/3. Значит `verify.ps1` шаг `workspace-tests` сейчас не проходит, и **ни один гейт закрыть нельзя**, чем бы его ни подтверждали. Механизм — в §5, D0.

**Третье — первопричина неэффективности агентов, и она измерена.** Между нормативной парой (24 251 строка, 1.17 МБ) и кодом (546 файлов, 7.0 M STU) **нет навигации ни в одну сторону**:

```
ARCH-* якорей в книгах            58
ARCH-* якорей в коде               1   (ARCH-SEC-01, единственный на весь workspace)
файлов с любым якорем              5   из 546
refusals.csv: normative_anchor   UNKNOWN во всех 751 строках
conformance.toml: owner          UNKNOWN в 55 из 58, support UNKNOWN во всех 58
```

`reports/audit/ELIOT_MODEL_EFFICIENCY_20260814.md` называет цену прямо: после отключения **всех** MCP реальные многошаговые задачи всё равно накапливали `76 917 – 118 856` cached input tokens, и источник — «агенты читали почти мегабайтную Implementation, прочие authority-документы, исходники и вывод Cargo».

Агент читает книгу целиком не от недисциплинированности. **Он читает её потому, что искать негде.** W0-10 доказал механизм на одном примере: нормативные имена `BootstrapBriefCompiler` и `CurrentSystemEvidenceCompiler` давали **ноль** вхождений, а способность была написана под именем `compile_provider_gap_brief`. Формулировка v1.4 дословно: *«следующий исполнитель не найдёт уже написанного — механизм, которым прошлая кампания делала „правильные“ реализации недостижимыми»*.

Там же v1.4 отложила общий случай: *«связывание всех нормативных имён с кодом… решается отдельным WorkItem после закрытия W0»*. **W0 закрыт. WorkItem не открыт.** Это и есть старая работа, которую надо доделать, — см. §2.1.

**Правило самоограничения.** Пункт, который нельзя закрыть за одну сессию одного исполнителя, — не пункт, а `ContractChallenge` к этой директиве. Директива, породившая новую волну, недействительна.

### 2.1. Индекс якорь↔символ — единственная новая единица, и она отменяет работу

Отложенный в v1.4 WorkItem открывается сейчас, потому что он единственный сокращает стоимость всех остальных. Это **не новая инвентаризация — это join уже существующих артефактов**:

```
58 якорей               → уже извлечены gen-conformance.ps1 в docs/conformance.toml
граф кода               → уже есть: .codebase-memory, 54 134 узла, 268 208 рёбер
крейты и fan-out        → уже есть: swarm/inventory/modules.json
блокировщики и сайты    → уже есть: swarm/inventory/refusals.csv
```

Выход — заполненная колонка `owner` в `docs/conformance.toml` **со стороны кода**, а не из Appendix H, плюс обратное направление: по символу находится якорь. Один генератор и один верификатор по образцу тех семи, что уже написаны и приняты.

Правило поддержания, не требующее процесса: **lane, который трогает сайт, записывает его якорь.** Пустой `owner` перестаёт расти сам.

Пока индекса нет, правило R3 («бриф без `architecture_and_implementation_refs` не выдаётся») исполнимо только на бумаге: подставить якорь неоткуда. Это объясняет, почему `normative_anchor` во всех 751 строке `UNKNOWN`, и почему это не лень исполнителя.

## 3. Четыре утверждения программы, опровергнутые кодом

**3.1. W4-01 не блокирован W3-04.**
Программа пишет: «подключить `eliot-mcp` как потребителя выделенного в W3-04 `mcp_stdio`». Манифесты говорят иначе:

```
eliot-mcp зависит от: eliot-protocol, eliot-receipts, eliot-security-contracts, serde/schemars/sha2/thiserror
eliot-cli уже несёт:  eliot-protocol, eliot-receipts
```

Ни `eliot-app`, ни `mcp_stdio` в цепочке нет. Крейт спроектирован под инъекцию: трейт `KernelGovernorPort`, null-объект `NoProviderPort`, типизированный `PortFailure`. **Ребро `eliot-cli → eliot-mcp` свободно сегодня, цикла не создаёт, W3-04 не ждёт.**

Честный результат: 21 сайт перестаёт называть блокировщиком существующий крейт и начинает называть настоящий — «не инъектирован admitted Kernel/Governor провайдер». Фронт сдвигается на один шаг и становится виден. Ложная метка «блокирован `eliot-mcp`» — ровно та болезнь, ради которой программа написана.

Объём склейки за манифестом lane измеряет и докладывает. Больше одной сессии — `ContractChallenge`, а не тихое расширение.

**3.2. R1 в форме `todo!()` неприменим, и это правильно.**
`todo!()` паникует. 111 сайтов отказывают типизированно и несут `dependency`/`detail` — это **строго лучший** маркер. Ставить туда `todo!()` значит менять graceful refusal на панику.

R1 амендится:

```
канонический маркер незавершённого := типизированный вариант PlanGap / *::Unimplemented
реестр незавершённого              := swarm/inventory/refusals.csv (принят, генерируем, верифицируем)
docs/UNIMPLEMENTED.md              := биекция по todo!-маркерам; честно пуст, таким и остаётся
```

Ноль правок продукта, ноль правок скриптов. Отмечено отдельно, потому что напрашивается неверное решение: **расширять источник `gen-unimplemented.ps1` строками CSV нельзя** — независимый оракул `verify-unimplemented.ps1` требует, чтобы якорь был реальным нормативным заголовком, а строки CSV несут `normative_anchor: UNKNOWN`. Пара генератор/верификатор сломается. Чинится правило, а не механизм.

**3.3. DoD W3 ссылается на несуществующий гейт.**
`measure-stu.ps1` возвращает `PROVISIONAL_NON_BLOCKING` и `exit 0` при любом значении, и меряет только git-tracked файлы — то есть слеп к продукту текущей волны. Ссылка снимается. Гейт включается только вместе с расширением области измерения; отдельной волной это не становится.

Дополнительно: **порог STU не архитектурен**. `A2.3` дословно: *«Architecture не задаёт максимальный размер, количество строк, tokens, files, packages или Modules… Split/merge решается по Effective Context Profile, dependency fan-out, build/test cost, failure isolation, replacement cost и Product Pulse»*. W3 резал по размеру при неработающем Pulse — то есть без одного из названных архитектурой входов решения.

**3.4. W3 отчитался разрезом на cells, а произвёл разгрузку контекста. Это разные утверждения.**
`A2.3` требует от micro-module: одна причинная ответственность и один lifecycle owner, **явный public contract**, typed dependency ports, one-way направление, **независимая proof surface**, границы failure/replacement/migration/removal.

Факт на дереве:

```
eliot-installation: 8 модулей объявлены как private `mod X;` (не `pub mod`);
                    7 из 8 содержат ноль #[test]; ни одного нового крейта;
eliot-host:         26 private `mod`, часть объявлена посреди файла (:448, :513, :833, :3958);
DoD W3 гласит:      «каждый новый крейт имеет ModuleTestCapsule с ненулевым числом тестов».
```

W3-02 не создал ни одного крейта, поэтому этот DoD к нему неприменим — и не выполнен. Предъявленное доказательство корректности разреза — совпадение SHA-256 списка тестов до и после — **одновременно является доказательством того, что независимая proof surface не появилась**. Мера успеха и мера провала здесь одно и то же число.

Единственный артефакт W3, отвечающий `A2.3`, — `eliot-host-control-endpoint`: настоящий крейт с тремя собственными тестами.

Это **не обесценивает сделанное**. `A2.3` прямо называет разгрузку контекста текущим реальным драйвером: *«Потребность в меньших causal worksets сейчас следует из ограничений model context»*. Падение `eliot-installation` с 1 351 821 до 569 689 байт — настоящая польза. Требуется одно: называть её тем, что она есть. Записать в результатах W3 `CONTEXT_RELIEF`, а не `cells`, и не наследовать `FunctionalCapabilityCell`/`ModuleTestCapsule` без крейта, публичного контракта и собственных тестов.

## 6. CI и потолок доказательства

Квота GitHub исчерпана. Гонять на раннере час то, что локально идёт 16 минут, запрещено прямо. Но заметить нужно точно, **что** покупал hosted-прогон: не скорость и не значок, а независимость от ambient-состояния одной машины. Это воспроизводится локально:

```
CLEAN_CLONE_ATTESTED :=
  клон закоммиченной ревизии в изолированный корень вне рабочей копии
  + свой CARGO_TARGET_DIR + свой TEMP + без ProgramData/демона/тёплого target
  + pwsh -NoProfile -File scripts/verify.ps1 → exit 0
  + записаны: ревизия, дайджест дерева, время, вывод одиннадцати шагов
```

Один прогон **на гейт волны**, не на WorkItem; цена — одна холодная сборка. Luna-C повторяет из своего клона: это и есть независимость, которой добивались от раннера. Внутри lane достаточно тёплого прогона по своему крейту. **До починки D0 такой прогон невозможен — он упадёт на `workspace-tests`.**

Две правки, по строке:

- `.github/workflows/ci.yml:70` — `-ne 125` → `-ne 126` (текст throw на `:71`). Воркспейс уже 126 после `eliot-host-control-endpoint`; сейчас workflow лжёт и упадёт на первом push. Крейт добавляется — число правится тем же коммитом.
- Блок `on:` (`:7–13`) сводится к `workflow_dispatch`. Тогда `[skip ci]` не нужен как дисциплина и квота не тратится случайно; после этого `[skip ci]` в сообщениях не ставится.

## Приложение. Противоречия, требующие явного решения Sol

Каждое проверено на дереве. Ни одно не закрывается работой — все закрываются записью.

**П1. Гейт W0 закрыт на невыполненном собственном proof.** `ROOT-DIRECTIVE-v1.4` задаёт для `W0-09` proof: *«Зелёный hosted receipt на main»*. Гейт закрыт с `HOSTED_NOT_RUN`. Отклонение записано честно — owner, причина (квота), риск, rollback. Но rollback гласит *«restore the hosted-green W0-09 criterion»*, а квоты нет. **Recoverable Deviation, условие пересмотра которого не может наступить, — не recoverable.** Переобъявить как постоянный пониженный потолок с `CLEAN_CLONE_ATTESTED` вместо hosted; иначе каждый следующий гейт наследует отклонение, которое все считают временным.

**П2. Основание программы отсутствует в дереве.** `docs/audit/` пуст. `CODEX_SWARM_FAILURE_AUDIT_2026-08-24.md` и `ELIOT_CODEX_DEEP_ROOT_CAUSE_AUDIT_20260824.md` — документы, на которые программа ссылается как на своё основание, — недоступны исполнителям. Это прямое нарушение R3 самой программой. Внести или снять ссылку.

**П3. §2.2 программы не исполнена и отменена молча.** Обещание: брифы и результаты сериализуются в типах `eliot-swarm`, «сирота получает первого реального потребителя», «swarm говорит на языке ELIOT с первого дня». Факт: `eliot-swarm` — **ноль потребителей**; в `swarm/results/` **10 разных `schema_version`** (`eliot-external-audit-result-v1` ×15, `eliot.bootstrap-work-result.v1` ×14, `eliot-work-result-v1/v2`, `…-v4` и прочие); **ни один не имеет владельца в Rust** — все собираются literal-хэштейблами внутри семи PowerShell-генераторов. При этом `eliot-bootstrap` содержит настоящие типы (`NormativePair`, `CurrentSystemEvidenceSnapshot`, `BootstrapRuleCatalogue`), которыми swarm не пользуется.

Следствия, которые надо признать вслух: заявленный dogfood не является dogfood; рост версий схем (`v1→v4`) — это и есть механизм переделок, ради которого v1.4 пришлось законодательно объявить «текущие попытки последние»; **область W7 больше, чем записано** — там не «замена файлового транспорта», а перенос семантики, которой в типах ELIOT никогда не было.

**П4. Порядок волн против `ARCH-DEV-01`.** `A0.8` определяет первый полезный vertical spine, и его первый пункт — *«один реальный agent bridge»*. `bins/eliot-agent-bridge` возвращает безусловный `Err(KernelAdmissionRequired)` и выходит с кодом 69. `ARCH-DEV-01`: *«Working system before broad hardening. Сначала создаётся реальный end-to-end cognitive loop; тесты и глубина добавляются по наблюдаемым failure modes»*. Программа применяет это правило явно, чтобы отложить W6, — и не применяет к себе: W0 (lint-политика, STU-измеритель, проекция норматива, verify-профиль) и W3 (разрезы) суть broad hardening, выполненные до существования spine. Это же объясняет, почему §2 настоящей директивы ставит фронтом провайдер №1, а не следующий разрез.

**П5. Conformance недоказуем по построению.** `A0.8`: *«Соответствие подтверждается живой conformance map A6.7»*. `A6.7` требует связи `ARCH-*` с owner, mechanism, failure behavior и observable status. `docs/conformance.toml`: 58 требований, `owner` UNKNOWN в 55, `support` UNKNOWN во всех 58, списки invalidation пусты. Форма карты есть, содержания нет. Закрывается §2.1, другого пути нет.

**П6. Маршрутные документы разошлись с деревом.** `docs/PROJECT_MAP.md` заявляет 125 workspace members, `.github/workflows/ci.yml:70` требует ровно 125, `cargo metadata` даёт **126**. Тот же класс дрейфа, что и в П5: артефакт, который никто не пересчитывает при изменении. Правило из §6 распространяется на PROJECT_MAP.
