## Headline structural fact (read this before the table)

There are **two parallel, non-communicating cognition stacks** in this repo:

| | Stack A — legacy/donor, actually reachable | Stack B — architecture-conformant rewrite |
|---|---|---|
| Crates | `crates/eliot-app` (produces the binary literally named `eliot-governor`, see `crates/eliot-app/Cargo.toml:8-10`), `crates/eliot-engine`, `crates/eliot-store`, `crates/eliot-types` | `crates/smart/*`, `crates/governor/*`, `bins/eliotd`, `bins/eliot-dreamer` |
| Size | ~190k lines | `crates/smart/*` = 3,861 lines |
| Wiring | Serves every `eliot_*` MCP tool (`crates/eliot-app/src/mcp_stdio/dispatch.rs`) | **`crates/smart/*` has zero dependents anywhere in the workspace.** Verified: `grep -rn "eliot_context::\|eliot_cues::\|eliot_memory::\|eliot_epistemic::\|eliot_understanding::\|eliot_dreamer_core::\|eliot_memory_curation::\|eliot_system_experience::"` returns exactly one hit outside those crates' own directories: `crates/smart/eliot-understanding/src/lib.rs:14` (uses `eliot-context`). |
| CI | Reachable? `bins/eliot` deps do not include eliot-app either — see Confidence | `Cargo.toml:127-134` `default-members` = `bins/eliot`, `eliot-host`, `eliot-kernel`, `eliot-store-surreal`, `eliot-watchdog`, `eliotd`. No `crates/smart/*`, no `crates/governor/*`, no `bins/eliot-dreamer`. |
| Tests | `crates/eliot-engine/tests/*`, `crates/eliot-app/tests/*` present | `crates/smart/*` has **no `tests/` directory at all** and exactly one inline test (`crates/smart/eliot-context/src/lib.rs:711-733`, asserts enum declaration order). |

`crates/governor/eliot-governor/src/lib.rs` is a service-lifecycle state machine (`ServiceId`, `GovernorState`, `admit_service`) — it contains **no cognition**. The name collision with the `eliot-governor` binary produced by `crates/eliot-app` is a real trap.

So: when this report says IMPLEMENTED, it means Stack A. When it says SHELL because "nothing calls it", that is almost always Stack B.

## Gaps ranked

- **[P0] The Dreamer binary cannot run, and no curation loop exists anywhere** — `A9.1`/`A9.2` make Dreamer the owner of background curation, interactive orientation, clarification and research synthesis, always returning candidates. `bins/eliot-dreamer/src/main.rs:15-26` is a program whose only observable behaviour is printing a `KERNEL_ADMISSION_REQUIRED` error and exiting 78; every transport method is a hardcoded `Err` (`bins/eliot-dreamer/src/lib.rs:146-191`); the only code that ever constructs a `DreamPacket` or `CurationCandidate` is compiled out of release builds (`#[cfg(test)]` at `lib.rs:434` and `lib.rs:516`). Meanwhile `grep -rni "dreamer" crates/eliot-app/src crates/eliot-engine/src` = 0 hits, so the running stack has no Dreamer either. Everything `A9` promises — Observation Candidate triage, episode reconstruction, duplicate/false-merge repair, Failure Fingerprints, reconsolidation and forgetting candidates — is currently produced by nothing.

- **[P0] Negative memory never blocks anything** — `A14.3` and `A7.1` make negative memory a load-bearing safety element of the Active View, and `A7.10` names a `where-not-apply` guard. `NegativeMemoryGate::evaluate_scoped` (`crates/eliot-engine/src/memory_lifecycle.rs:825`) implements exactly that gate, correctly, and is called **only from the `#[cfg(test)]` module starting at `memory_lifecycle.rs:1158`**. In production, failure fingerprints are decorative packet text (`context.rs:1927`) that is discarded 4th under budget pressure (`context.rs:3463`). A repeated failure therefore cannot be blocked, and no reopen-condition/discriminative-evidence requirement is ever enforced.

- **[P0] The Decision Safety Floor is not the safety floor** — `I7.11` requires goal/acceptance, authority/fence, material unknowns/conflicts/negative memory, and the applicable verifier to be `NON_DROPPABLE`, and requires `DECISION_CONTEXT_INCOMPLETE` when the floor cannot be delivered. `mandatory_floor` (`crates/eliot-engine/src/context.rs:3337`) trims *everything* `trim_next` will trim and protects only the caller-supplied `candidate_handles` (`context.rs:3500`). The shed order at `context.rs:3460-3499` puts `open_questions`, `negative_memory` and `current_truth` ahead of the requested handles. `DECISION_CONTEXT_INCOMPLETE` and `ContextAtomPolicy` do not exist in the codebase. Under budget pressure the compiler will silently (well — traceably, but without refusal) return a packet missing every element the architecture calls non-droppable.

- **[P1] Theory Portfolio / epistemic fitness is completely absent** — `A5.3` ("theories earn and lose weight through outcomes") and `I12.22` (`TheoryModel` with `operational_status: candidate\|usable\|preferred\|contested\|stale\|refuted`, transfer/revalidation, `ConflictSet(kind=theory_conflict)`) have **no code at all**: zero grep hits for `TheoryPortfolio`, `TheoryModel`, `theory_id`, `epistemic_fitness`. This is one of the two claims that most distinguishes ELIOT from RAG, and it is unimplemented. The closest thing shipped is a 4-bucket status split (`context.rs:2027`) that collapses all rivals into one `conflicted: Vec<String>`.

- **[P1] Skills never reach the compiled packet, so the skill guard is never enforced there** — `A7.10` + `I7.12`. `ContextCompiler::compile_with_skills` (`context.rs:692`), the only function that runs `SkillDistractorFilterService::procedural_packet` into a packet, has zero callers; `empty_packet` hardcodes `procedural_skills: ProceduralSkillPacketView::default()` (`context.rs:1975`).
