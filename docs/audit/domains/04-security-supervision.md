## Gaps ranked

- **[P0] Agent-facing IPC peer attestation is TOCTOU and drops the anti-race handles the IPC crate deliberately holds.** `A12.1`/`ARCH-SEC-01` requires a breach to gain no hidden authority; `A12.2` binds Principal at admission.
  The chain in the production `eliot-governor` daemon (`crates/eliot-app/src/commands/operations.rs:611,679` binds and serves this pipe):
  1. `crates/eliot-windows-ipc/src/lib.rs:376-385` `named_pipe_client_process` calls `GetNamedPipeClientProcessId` (`:381`) then `open_process_identity(pid)?.identity` — the `?.identity` field access **drops the surrounding `ObservedProcess`**, releasing both `_process: OwnedHandle` and `_image_file: PinnedFile` (constructed at `:420-441`). The crate's own doc comment at `:443-450` states these handles exist precisely to prevent "PID reuse and executable replacement between verification and termination".
  2. `crates/eliot-app/src/named_pipe_ipc.rs:858-870` `ClientProcessAttestation::from_kernel_identity` then discards `file_identity` (the `..` at `:861`), calls `image.canonicalize()` — re-resolving **by name**, following reparse points that `PinnedFile::open` explicitly refused (`FILE_FLAG_OPEN_REPARSE_POINT`, `eliot-windows-ipc/src/lib.rs:120`) — and re-reads the file with `sha256_file` (`:1090`, plain `fs::read`, default share mode).
  3. `crates/eliot-app/src/named_pipe_ipc.rs:1065-1085` `authenticate_attested_governor` grants the privileged `cognitive_governor` / `host_governor` profiles on that identity. It re-hashes the file a third time (`:1080-1084`) to catch a swap — a check-check, not a check-use; nothing holds the file open across the window.
  4. `ProcessImageIdentity` (`eliot-windows-ipc/src/lib.rs:82-89`) carries **no process start time**, so PID reuse between step 1's `GetNamedPipeClientProcessId` and step 2's `OpenProcess` is structurally undetectable.
  **Why P0:** `authenticate_private_governor_handshake` (`:1041-1063`) checks the *same* `self.token_hash` as the ordinary `eliot_ipc_handshake` profile (`:952-957`). Every token-bearing client already holds that token — it is how any MCP agent connects. The process attestation is therefore the **sole** boundary separating a `dynamic_agent` from `cognitive_governor`/`host_governor`. Winning the image/PID race is authority laundering by a supervised agent, exactly what `A8.5` and `ARCH-SEC-01` name.
  **Precondition (stated so it can be re-judged):** attacker must run as the same Windows user and hold the IPC token; Windows offers no strong same-user boundary independently. The defect is provable from source; practical exploitability was not measured (product not running).
  **The correct implementation already exists in this repo** and is not used here — see the divergence section.

## Divergences where CODE looks RIGHT and the DOC looks stale

- **The Kernel-side peer authentication is materially stronger than anything the architecture asks for, and it is the model the agent-facing path should have copied.** `crates/kernel/eliot-platform-windows/src/lib.rs:5813` `authenticate_named_pipe_client` validates the pipe DACL, retains one process handle, reads identity **and** token from that same handle, impersonates the client only long enough to bind SID/session with an RAII `RevertToSelf` guard, and admits via `same_process_identity` (`:5733-5750`) which compares `process_id` **and** `start_time_100ns` **and** the canonical image path. `crates/kernel/eliot-ipc/src/lib.rs:95-117` `PeerIdentity::from_platform_evidence` then composes a `ProcessBinding` carrying that start time, and `require_authenticated()` gates every `send_frame`/`receive_frame` (`:1399`, `:1418`). The docs (`I15.8`) only say "Watchdog detects unexpected client/process/path activity" — the code implements a far stronger handle-bound, start-time-bound, impersonation-verified identity than the doc describes. **The architecture text should be updated to make this the normative requirement for every ELIOT pipe**, which would also make the P0 above a conformance failure rather than an unstated asymmetry.
- **The pre-persistence secret boundary is an unspecified but valuable control.** `crates/eliot-types/src/secret_boundary.rs:69` `inspect_secret_bytes` — bounded, deterministic, ASCII-oriented, and deliberately category-only (`SecretBoundaryViolation` carries neither the matched value nor a digest of it, `:50-54`) — plus the zeroizing `admit_provider_output` at `crates/eliot-app/src/cognitive_runner.rs:1470-1487`. A12.6 asks only for "no plaintext leakage"; the code implements an actual enforcement point the doc never names.
- **`eliot-source-assurance` is a faithful, complete rendering of `I15.5`** (`crates/security/eliot-source-assurance/src/lib.rs:117-330`), including the requirement that quarantine be "an explicit status, not a hidden boolean" (`QuarantineStatus:184`) and that no non-admitted state loses its reason (`AdmissionOutcome:306`). The contract layer is ahead of the implementation doc; only the wiring is missing.
