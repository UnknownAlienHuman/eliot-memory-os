## Gaps ranked

- **[P0] Every successful canonical write is reported to the Kernel as permanently unknown.**
  `I5.19` requires a terminal receipt returned by identity, and `A12.3` requires the transition to end in a canonical receipt. The commit *does* land durably (`apply.rs:920-1146`). But `plan.rs:153` sets `envelope: None`, so `require_reconciliation_envelope()` (`eliot-store-api/src/lib.rs:989-993`) fails, so `StoreResponse::from_transaction_receipt` (`wire.rs:318-333`) — the only production conversion, at `bins/eliot-store-surreal/src/lib.rs:683` — emits `Unknown { reason: "receipt_envelope_missing" }`. The Kernel then falls back to `receipt_exact` (`crates/kernel/eliot-kernel-service/src/store_client.rs:384-393`), which re-reads via `Request::Receipt` → `from_receipt` (`bins/eliot-store-surreal/src/lib.rs:696`) → the **same** envelope check → `Unknown` again → `StoreError::Unavailable` (`store_client.rs:276-281`). The loop is non-recoverable by construction: durable effect applied, outcome permanently unprovable. This is the exact failure mode `I5.19` forbids ("no final `dead_letter` receipt is fabricated… the gap is open"), except here it happens on the success path. `StoreResponse::validate` (`wire.rs:365-372`) rejects the response too, so even a hand-built envelope-less receipt cannot cross the wire.

- **[P0] Two canonical writers ship in two binaries against one table name — `ARCH-SEC-02` violation.**
  `A12.3`: "Direct storage access… или второй writer являются security/integrity problem". Writer A: `crates/storage/eliot-store-surreal-adapter/src/apply.rs:440`, shipped in `bins/eliot-store-surreal` (a default CI member). Writer B: `crates/eliot-store/src/canonical_store.rs:2321` → `surql/apply_write_envelope.surql:461` `UPSERT type::record('write_receipt', $receipt_id)`, shipped in the `eliot-governor` binary (`crates/eliot-app/Cargo.toml:8-10`). Both own a table named `write_receipt`, with mutually exclusive unique indexes (`schema.rs:44` `operation_id UNIQUE` vs `surql/000_schema.surql` `idx_receipt_write … write_id UNIQUE`) and disjoint field sets (`operation_id`/`idempotency_key`/`body` vs `receipt_id`/`write_id`/`input_hash`/`project_sequence`). Pointed at the same namespace they corrupt each other; pointed at different namespaces there are two canonical histories. Neither writer detects the other. Additionally B's `migrate_schema` (`canonical_store.rs:2179`) issues bare `DEFINE … OVERWRITE` DDL on every call, which would silently rewrite A's indexes.

- **[P1] No admission front door: `WriteSubmission` is absent, and no non-committed receipt can be produced.**
  `I5.19` requires three non-collapsed outcomes and a `WriteSubmission` returned before any final receipt. `grep -rn "WriteSubmission" crates/ bins/ --include=*.rs` → nothing. `build_receipt` (`plan.rs:123-155`) hardcodes `status: WriteReceiptStatus::Committed`; `Rejected` / `DeadLetter` / `Cancelled` are declared at `eliot-store-api/src/lib.rs:874-877` and never constructed. `SequenceGap` and `SequenceDisposition` do not exist in `crates/storage/`. Consequence: a rejected or cancelled operation has no canonical control transition and its reserved ordering position has no disposition — exactly the "SequenceGap requires disposition" obligation in `I5.19`.

- **[P1] The physical schema is ~15% of `Appendix N`, and the `migrations/` directory is dead.**
  `Appendix N.2/N.3/N.4` name ~150 tables; N.6 names ~75 indexes. Path A defines 9 tables and 9 indexes (`schema.rs:32-74`); path B defines 44 tables (`crates/eliot-store/src/surql/0*.surql`) that mostly are not N tables (`claim_card`, `tool_observation`, `canonical_record`, `scope_head`, `ul_*`, `memory_search_*`). Absent from both: `audit_record`, `purge_ledger`, `sequence_gap`, `sequence_disposition`, `problem_state`, `critical_attention`, `operation_job`, `module_catalog`, `blob_ref`, `scope_revision_view`, `work_scope`, `principal`, `agent_session`, `policy_snapshot`, `approval_request/record`, `authority_activation/revocation_record`, `capability_grant`, `observation_domain`, `disclosure_*`. Meanwhile `migrations/0001_bootstrap.surql` — the directory an operator would reasonably treat as the schema of record — contains only `health_record` and `migration_record`, is 9 lines long, and is referenced by no Rust code.

- **[P1] The new blob store has no production backend; the new backup crate has no consumer.**
  `I5.12` requires an active-owner CAS with AEAD envelopes, key lineage and tombstoned GC. `crates/storage/eliot-blob/src/lib.rs` implements all of it (`stage_locked:1637`, `reachability:2047`, `gc:2091`), but `#[cfg(test)]` starts at `:2596` and every port impl is inside it: `BlobPlatformPort:2633`, `BlobKeyPort:2782`, `BlobAeadPort:2809`, `BlobLiveSetPort:2862`. `BlobStoreService::new` is called only at `:2998`/`:3015` (tests). Same shape for `crates/storage/eliot-backup`: a real journaled resumable restore (`:1085-1250`) whose `RestoreTarget`/`RestoreJournalPort` exist only at `:1776`/`:1732` inside `#[cfg(test)]` (from `:1719`), and on which **no workspace crate depends**. The blob functionality that actually runs is the older `crates/eliot-store/src/blob_store.rs` + `crates/eliot-engine/src/safety.rs` pair, which has no encryption, no key lineage and no `BlobReadyReceipt`.

- **[P1] Privacy erasure and the purge ledger are unimplemented.**
  `A4.7` makes physical existence an independent property and `I5.14` enumerates seven erasure targets plus a purge receipt; `A13.7`/`ARCH-RES-03` requires restore to preserve purge closure. `crates/security/eliot-erasure/src/model.rs:65-79` declares `ErasureBackend::erase` / `append_purge_ledger`; **no type implements it**, no crate depends on `eliot-erasure`, and no `purge_ledger` table exists in either schema. Restore therefore cannot refuse to resurrect purged payload — it has nothing to consult (`safety.rs:809-926` performs no purge check).

- **[P2] Blob GC is fail-closed but hard-capped at 512 records, so it cannot run on a real corpus.**
  `blob_reference_snapshot` (`canonical_store.rs:5065-5080`) issues **one** `BlobReferenceScan` with `limit.clamp(1, MAX_BLOB_REFERENCE_RECORDS)` where the constant is `512` (`canonical_store.rs:42`); `surql/blob_reference_scan.surql:2-8` clamps identically server-side and fetches `limit + 1` to detect overflow. `build_blob_reference_snapshot` then sets `complete = records.len() <= limit && …` (`canonical_store.rs:5198-5200`), and `validate_reference_snapshot` (`safety.rs:3129-3134`) aborts GC when `!complete`. The safety behaviour is correct; the consequence is that once the canonical store exceeds 512 blob-referencing records, GC permanently refuses and blobs accumulate forever. There is no pagination loop.

- **[P2] Restore receipts assert verification with hardcoded literals, and check none of the six A13.7 restore obligations.**
  `safety.rs:938-939` (also `:747-748`, `:790-791`) writes `verified_manifest: true, verified_checksums: true` as constants into `RestoreReceipt`, not derived from any verification result. The 5 checks actually run (`safety.rs:846-877`) cover target isolation and approval only — schema/format compatibility, provenance/integrity closure, privacy purge closure, semantic inheritance preservation, Authority Epoch monotonicity and external-effect reconciliation are all unchecked. The one genuine end-to-end proof (`crates/eliot-engine/tests/operations_runbook.rs:26`) silently returns `Ok(())` when `ELIOT_SURREAL_EXE` is unset (`:27-30`), and `eliot-engine` is outside the default CI member set — so it is not currently proving anything.

- **[P2] Receipt `committed_at` is a sequence label, and `commit_id` is a formatted string.**
  `I5.19` lists `commit_id` and `committed_at` as terminal receipt fields; `A5.4` requires valid/known/transaction time on load-bearing state. `plan.rs:47` sets `committed_at = format!("commit-sequence-{next_commit_sequence:016}")` and `plan.rs:88` sets `commit_id = format!("commit-{operation_key}")`. `apply_migration` proves the clock port is available and enforced (`apply.rs:335-345`), so this is an omission on the write path, not a missing capability. A real SHA-256 payload digest *is* computed at `plan.rs:90-92` but is written only into outbox rows (`plan.rs:270`), never into the receipt.

- **[P2] Typed relations are collapsed into one untyped table on the new path.**
  `Appendix N.5` requires explicit relation tables carrying scope, provenance and epistemic status, and forbids a derived relation satisfying an authority/verification/causal query. `apply.rs:1057-1078` writes every relation into `relation_record` with a free-text `relation_kind`, a synthetic `relation_id = format!("relation-{operation_id}-{index}")`, and only `operation_id` + `state_fence` — no endpoints, no direction, no epistemic status. Nothing distinguishes `verified_by` from `resembles`.

- **[P2] Two raw-SQL sites outside the named-operation registry — neither is injectable, one risks credential leakage.**
  (a) `crates/eliot-store/src/canonical_store.rs:2243`: `format!("SELECT * FROM {table} LIMIT {SECRET_SCAN_PAGE_SIZE} START {start};")`. `table` iterates the compile-time const `SECRET_SCAN_TABLES` (`:54`), the other two are a const and a `usize` — **no injection**, but it bypasses the closed registry.
  (b) `crates/eliot-store/src/surreal_server.rs:309-311`: `format!("DEFINE USER OVERWRITE root ON ROOT PASSWORD {password_literal} …")` where `password_literal = surrealql_single_quoted(current.expose_secret())`. The escaper (`:893-896`) escapes `\` and `'` correctly, so **no injection**; but the live credential is placed into a query *string* rather than a bound parameter, so any query-level logging or error echo on the transport would capture it — against `A12.6` "no command-line/plaintext leakage". No attacker-controlled string reaches SQL text anywhere in the storage layer.

## Divergences where CODE looks RIGHT and the DOC looks stale

- **`revision_head` key shape.** `N.6` asks for `revision_head(scope_id, revision_key) UNIQUE`. The code uses a single-column unique index on `revision_key` (`schema.rs:49`) where the key is itself `format!("scope:{scope_id}")` (`plan.rs:196`). Same uniqueness guarantee, fewer columns; the appendix explicitly permits combining tables when "logical contract identities… remain unchanged" (Appendix N preamble). Not a defect.

- **`UnknownOutcome` discipline exceeds the written contract.** `apply.rs:1118-1128` treats *only* the six named `THROW` markers as deterministic conflicts and everything else as unknown, with an explicit comment that the transport cannot prove whether COMMIT ran. `I5.19` describes unknown-commit handling but does not spell out this narrow allow-list. The code is stricter and more correct than the prose; the doc should adopt it.

- **`Appendix N` self-labels as stale.** Its own header reads "Status: TARGET / PHYSICAL PROFILE HYPOTHESIS; CURRENT SUPPORT ABSENT/PARTIAL", and `I5.9` states the audited source lineage "remains non-conformant". Rows 12/13 above are therefore a *measured* gap against a target the doc already concedes is unmet — they are not a surprise, but the size of the gap (9 of ~150 tables) is larger than "PARTIAL" suggests.
