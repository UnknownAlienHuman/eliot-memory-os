# ELIOT — программа восстановления и каркас работы swarm, v1

**Основание:** `docs/audit/CODEX_SWARM_FAILURE_AUDIT_2026-08-24.md`
**Норматив:** `ELIOT_ARCHITECTURE.md 4.5-draft` + `ELIOT_IMPLEMENTATION.md 0.29-draft` (SHA-256 сверены)
**Состав:** Sol (Codex main) + Luna-A/B/C (Codex sub) + 5 Ox Alpha (OpenCode Go) + 2 Ox Alpha (OpenRouter) + Antigravity (Gemini 3.7 flash)
**Статус документа:** каркас и основные задания. Мелкие решения — за Sol. Это не третья нормативная книга и не источник authority.
**Ревизия:** v1.1 — учтены проверенные находки внешнего аудита `ELIOT_CODEX_DEEP_ROOT_CAUSE_AUDIT_20260824.md` (что принято и что отклонено — Приложение В).

## 0. Как читать и кто что решает

| Уровень | Кто | Что фиксирует |
|---|---|---|
| Норматив | Architecture + Implementation | смысл, границы, контракты |
| **Программа (этот файл)** | человек + аудит | порядок волн, роли, правила, DoD волн |
| План | **Sol** | какие `WorkItem` в текущей волне, кому, в каком порядке |
| Брифы | **Sol → Luna** | один `AgentWorkUnitBrief` на исполнителя |
| Исполнение | Luna / Ox / Antigravity | код, evidence, `ContractChallenge` |

Этот файл **не** содержит: списка файлов для правки, порядка коммитов, распределения по конкретным агентам внутри волны. Это решает Sol.
Этот файл **содержит**: правила, которые Sol не имеет права ослабить, форму задания, границы волн и условия перехода между ними.

Один принцип, из которого выведено всё остальное:

> Провал предыдущей кампании произошёл не от нехватки агентов и не от нехватки кода.
> Он произошёл от того, что агент **не мог отличить несделанное от сделанного**, **не мог увидеть продукт живым** и **не мог поместить единицу работы в контекст**.
> Программа чинит эти три вещи первыми. Всё остальное — после.

## 1. Топология: агенты и роли

### 1.1. Отображение на роли книги

| Исполнитель | Роль по `A2.2` / `I17.15` | Делает | **Не делает** |
|---|---|---|---|
| **Sol** (Codex main) | Main Agent + Task Compiler | замораживает contract revision, компилирует `WorkItem`, принимает/отклоняет результаты, решает спорное, объявляет гейты волн | не пишет код, **не читает исходники**, не интегрирует, не запускает внешних агентов напрямую |
| **Luna-A** | Integration Owner | принимает `IntegrationCandidate`, гоняет Edge proof и Product Pulse, мержит, ведёт lane-реестр | не пишет фичи, не принимает собственные результаты |
| **Luna-B** | Fleet Manager (Agent Coordinator) | раздаёт брифы 8 внешним агентам, следит за lane/claim, собирает structured result, отбраковывает мусор, эскалирует | не мержит, не решает архитектурное, не переписывает контракт |
| **Luna-C** | Independent Verifier | **включается только на гейтах волн**: независимо проверяет, что DoD выполнен, и пытается его опровергнуть | не участвует в исполнении волны, не видит рассуждений Luna-A до собственной submission |
| **Ox Alpha ×5** (OpenCode Go) | Workers, механические единицы | ограниченные детерминированные единицы: генераторы, инвентаризация, вынос тестов, split по готовым границам, локальные починки | не меняют public contract, не трогают чужой lane, не интегрируют |
| **Ox Alpha ×2** (OpenRouter) | Auditors / Challenge | **независимый** аудит и фальсификация: «докажи, что вывод неверен» | не видят выводов sibling-агентов до собственной submission (`A10.6` Independence Profile) |
| **Antigravity** (Gemini 3.7 flash) | Scanner | массовые read-only проходы: подсчёты, карты, «падает ли дискриминатор на старом пути», генерация капсул | ничего не пишет в основную ветку |

### 1.2. Управление

```text
человек
  └─ Sol ──────────────────────────────── решения, контракты, гейты
       ├─ Luna-A  ── Integration/Proof ── worktree integ/*, мерж, Pulse
       ├─ Luna-B  ── Fleet ───────────┬── Ox Alpha ×5   (OpenCode Go)
       │                              ├── Ox Alpha ×2   (OpenRouter, independence)
       │                              └── Antigravity   (scan)
       └─ Luna-C  ── Independent Verifier (только на гейтах)
```

Sol общается ровно с тремя адресатами (Luna-A, Luna-B, и на гейтах Luna-C). Все внешние агенты видны Sol только как агрегированный результат от Luna-B.

### 1.3. Правило стоимости

Sol дороже Luna примерно в 10×. Отсюда жёстко:

```text
Sol на вход получает:   бриф-запрос, structured result, ContractChallenge, отчёт гейта.
Sol на вход НЕ получает: исходники, диффы целиком, транскрипты внешних агентов,
                         whole-project dump, содержимое дампов и логов.
```

Если Sol понадобился код — это сигнал, что бриф составлен неверно: нужен не код, а `CrateContextCapsule` от Luna. `A10.6`: *«Whole-project dump и полные transcripts других agents не являются default»*.

**Измеренное, а не предполагаемое.** `reports/audit/ELIOT_MODEL_EFFICIENCY_20260814.md` фиксирует по этому проекту: после отключения **всех** MCP, инструкций, плагинов и policy-файлов (первый ход упал с `63 252` до `9 050` токенов) реальные многошаговые задачи всё равно накапливали **76 917 – 118 856 cached input tokens**. Остаточный источник назван прямо: агенты читали почти мегабайтную Implementation, прочие authority-документы, исходники и вывод Cargo.

Отсюда правило, которое дороже любого другого решения по стоимости:

> **Полная Implementation — источник разворачивания, а не тело промпта.**
> В бриф попадают только те фрагменты, которые меняют решение. Всё остальное остаётся handle-ом.

Это не оптимизация расходов. Это причина, по которой агенты пропускали provider-контракты: значимое правило тонуло в объёме.

## 2. Субстрат координации на время bootstrap

### 2.1. Почему не через ELIOT

ELIOT не может сейчас управлять собственным swarm: `eliot-swarm`, `eliot-agent-coordinator`, `eliot-testd-core`, `eliot-instrument-runner` — сироты с нулём зависимых, три порта (`AgentRouteProvider`, `ReceiptVerificationPort`, `SwarmCheckpointProvider`) реализованы только в `src/repair_tests.rs`. Пытаться поднять их до старта работы — значит повторить предыдущую кампанию.

Поэтому транспорт координации на волнах W0–W4 — **git + файлы**, и только он. Это разрешено `I17.2`: до появления канонической памяти артефакты класса `BootstrapDraft` пишутся в репозиторий, **append-only, content-addressed, как evidence, но никогда как authority**.

### 2.2. Но формат — уже целевой

Ключевое решение, экономящее целую волну работы позже:

> Брифы и результаты сериализуются **в типах `crates/agent/eliot-swarm`** (`SwarmPlanProposal`, `AdmittedSwarmPlan`, `WaveAssignment`, `ReservedAssignment`, `TerminalWorkUpdate`, `ReviewCause`) в JSON.

Следствия:
- когда `eliot-swarm` получит исполняемого потребителя (W7), меняется только транспорт, не семантика;
- сирота получает первого реального потребителя, а её 3 952 строки — первый Edge proof;
- swarm, который строит ELIOT, с первого дня говорит на языке ELIOT. Это и есть dogfood, а не декларация о нём.

Если поле типа не покрывает нужду — это `ContractChallenge` к `eliot-swarm`, а не самодельное поле в JSON.

### 2.3. Раскладка

```text
swarm/
  plan/<wave>/plan.json          AdmittedSwarmPlan, подписан Sol, immutable внутри волны
  briefs/<work-item-id>.json     AgentWorkUnitBrief (профиль ниже)
  claims/<work-item-id>.json     write/path claims + BuildFingerprint + lane
  results/<work-item-id>.json    TerminalWorkUpdate + structured result
  challenges/<work-item-id>.md   ContractChallenge, если возвращён
  gates/<wave>.md                отчёт гейта + вердикт Luna-C
  inventory/                     артефакты волны W1
```

Всё это **в git**. Причина прямо в аудите: модель приёмки требует evidence, а `.gitignore` его выбрасывает. Каталог `reports/` для координации swarm не используется.

### 2.4. Изоляция записи (`I2.17` write isolation)

```text
один WorkItem                 → одна ветка work/<id>, один worktree, один writer;
один объявленный mutable scope → ровно один writer в волне;
пересечение path claim         → Luna-B отклоняет бриф до выдачи, а не после конфликта;
worker НЕ мержит свой результат → всегда Luna-A;
read-only аудиты               → fan-out без claim, параллельность не ограничена.
```

`BuildFingerprint`, отдельные `CARGO_TARGET_DIR` на lane и правило «один Cargo-producer на target root» — по `I18.26`. Никакой внешний агент не запускает `cargo --workspace` самостоятельно: только `cargo check -p <crate>` + `ModuleTestCapsule` своего cell + затронутые edges.

### 2.5. Потолок параллелизма задаётся пропускной способностью интегратора

Прошлая кампания дала точное измерение того, что бывает иначе. `docs/operations/RUNTIME_LIVE_V3_HANDOFF_2026-08-22.md:87`:

```text
273 зарегистрированных worktree;
257 локальных codex/* refs;
39 refs являются предками принятого baseline.
```

**85 % произведённой работы не дошло до принятия.** Производителей кандидатов было много, семантический гейт — один и дорогой. Добавление воркера увеличивает только длину очереди.

Поэтому WIP-потолок этой программы задаётся **не числом доступных агентов**, а тем, сколько Luna-A успевает принять:

```text
пока Pulse #1 красный:
  1 integration controller (Luna-A);
  не более 3 одновременных mutating lane;
  read-only fan-out не ограничен (claim не берётся);
  новый mutating lane не открывается, пока предыдущий не получил disposition.
```

У вас 11 агентов. Это **не** значит 11 параллельных write-lane. На волнах W0 и W2 одновременно пишут один-два; остальные работают в read-only режиме на W1/W3. Волна W3 — единственная, где 3 write-lane оправданы, потому что монолиты разрезаются по непересекающимся файлам.

### 2.6. Каждая единица работы обязана получить disposition

Ни один lane не закрывается «на потом». Ровно одно из четырёх:

```text
INTEGRATED             — принят и слит;
REJECTED_WITH_EVIDENCE — отклонён, evidence сохранён, ветка архивируется;
SUPERSEDED             — заменён другим кандидатом, причина записана;
PRESERVED_DONOR        — не интегрируется, но сохраняется как донор, с указанием, чего именно.
```

После disposition: worktree удаляется, build-root получает TTL, сырые логи и дампы получают потолок в байтах, ref остаётся только при forensic/донорской ценности. Именно отсутствие этого правила произвело 273 worktree и 31.8 ГБ поздней уборки.

## 3. Четырнадцать правил, которые Sol не имеет права ослабить

Каждое чинит конкретный механизм провала из аудита.

**R1. Незавершённость маркируется, а не отказывается.**
Нет реализации — `todo!("<ARCH-якорь>: <что именно>")` и строка в `docs/UNIMPLEMENTED.md`. Fail-closed отказ допустим **только** как спроектированное поведение и обязан нести отдельный тип, а не общий `Unavailable`.
*Чинит: 1371 отказ, неотличимый от реализации.*

**R2. Единица работы помещается в контекст, иначе возвращается challenge.**
Бриф несёт измеренный `loaded_slice_STU` и `agent_workset_STU`. Если workset не влезает — исполнитель **обязан** вернуть `ContractChallenge`, а не начинать. Молчаливая работа по неполному срезу — дисциплинарный отказ результата.
*Чинит: 450k STU в одном файле и двенадцать коммитов по одному дефекту.*

**R3. Норматив в дереве, и каждый бриф ссылается на якорь.**
`docs/normative/` — копия пары, сверяемая по SHA-256 в CI. Бриф без `architecture_and_implementation_refs` не выдаётся.
*Чинит: норматив по внешнему Windows-пути и один `ARCH-*` якорь на 589k строк.*

**R4. Каждая волна заканчивается наблюдаемым Product Pulse.**
Не отчётом, не зелёными unit-тестами, не голосованием агентов. Исполняемым end-to-end проходом в CI.
*Чинит: 132 из 132 E2E-теста выключены.*

**R5. Критерий приёмки не может ссылаться на несуществующего владельца.**
Перед выдачей брифа Sol проверяет: у всех evidence-владельцев в DoD есть хотя бы один реальный потребитель. Нет — сначала ребро, потом критерий.
*Чинит: дедлок семи paused-ячеек.*

**R6. Один mutating writer на объявленный scope.**
**R7. Worker не интегрирует собственный результат.**
**R8. Read-only fan-out свободен; write-lane выдаётся поштучно.**

**R9. Результат — структура, не проза.**
`artifacts, evidence, uncertainty, unresolved_questions, proposed_effects, evidence_lineage`. Проза может быть артефактом, но не заменяет поля (`A10.6`).

**R10. Независимость реальна.**
2 OpenRouter Ox Alpha и Luna-C не получают выводов остальных до собственной submission. Раскрытие поздних findings явно меняет Independence Profile и записывается.
*Чинит: «25+ external ACCEPT» как corroborating evidence — прямой анти-паттерн `A16.2`.*

**R11. Второй провал одного класса механизма → Mechanism Review, а не третья попытка.**
`I17.15`. Третьей попытки без смены гипотезы не бывает.
*Чинит: «two failed implementation/gate cycles» × 7 ячеек.*

**R12. Sol не читает исходники.**
Нужен код — переписывается бриф.

**R13. Provider раньше consumer, и это проверяется исполнением, а не наличием ID.**
Consumer-единица не выдаётся, пока у её провайдера нет **работающей операции** и дискриминатора, падающего на реальном ребре. Наличие cell ID, типа, схемы или fake-порта не считается готовностью провайдера.
*Чинит самый частый цикл прошлой кампании:* consumer требует provider-issued evidence → провайдер ещё не выдаёт поле/операцию → воркер делает локальный тип или caller-input → package-тесты зелёные → семантический гейт отклоняет authority laundering → новая ревизия ломает соседние cell-ы. Это происходило на `C0-12`, `C0-13`, `A-01/A-03/A-05`, `G-03`, `G-10`, `A-13` — то есть на всех paused-ячейках сразу.

**R14. Полная Implementation не подаётся в тело промпта.**
Только фрагменты, меняющие решение, плюс handle. Измерение из §1.3 — прямое основание.

## 4. Форма задания

### 4.1. Профиль брифа

`I17.14` определяет 28 полей `AgentWorkUnitBrief`. Заполнять все — ceremony, которую `I17.17` прямо запрещает. Обязательный минимальный профиль для этой программы:

```yaml
AgentWorkUnitBrief:            # профиль BOOTSTRAP-MIN
  work_item_id:
  wave:
  executor_class:              luna | ox-opencode | ox-openrouter | antigravity
  product_objective_and_causal_property:   # одно предложение, зачем это продукту
  architecture_and_implementation_refs:    # минимум один якорь ARCH-* / I-раздел
  primary_functional_cell:                 # что именно, не «файл»
  implementation_package_and_source_slice_refs:
  frozen_contract_revision:                # ревизия, замороженная на волну
  old_failing_behavior_or_missing_capability:
  discriminator_that_fails_old_behavior:   # ОБЯЗАТЕЛЬНО и ОБЯЗАТЕЛЬНО падает на старом пути
  one_hop_providers_and_consumers:
  allowed_effects_and_non_goals:           # non_goals не опционально
  loaded_slice_STU: / agent_workset_STU:   # измерено, не оценено
  expected_artifact_or_evidence:
  proof_command:                           # точная команда, которую исполнитель обязан прогнать
  product_pulse_ref:
  budget_stop_and_challenge_path:
  integration_owner:                       # всегда Luna-A, никогда сам исполнитель
```

Поля, не меняющие решение, не заполняются. Поля `discriminator_*`, `non_goals`, `*_STU`, `integration_owner` — **не опускаются никогда**.

### 4.2. Что обязан вернуть исполнитель

```yaml
TerminalWorkUpdate:
  work_item_id:
  disposition:  completed | challenged | blocked | failed
  artifacts:            # пути/коммиты
  evidence:             # вывод proof_command дословно, включая неуспех
  discriminator_before: # доказательство, что дискриминатор падал ДО правки
  discriminator_after:
  uncertainty:
  unresolved_questions:
  proposed_effects:     # что ещё придётся тронуть, но НЕ тронуто
  evidence_lineage:
```

`disposition: completed` без пары `discriminator_before` / `discriminator_after` не принимается. Это единственный барьер против proxy-оптимизации.

### 4.3. `ContractChallenge` — обязанность, не право

Исполнитель **обязан** вернуть challenge (`I17.14`), когда:

```text
дискриминатор измеряет прокси, а не свойство;
владелец/cell выбран неверно;
оракул контролируется тем же патчем;
Decision Safety Floor не помещается ни в один квалифицированный envelope;
пропущенное ребро меняет причинное объяснение;
несколько заданий конфликтуют по public contract или владельцу состояния.
```

Challenge — **успешный** исход единицы работы. Luna-B обязана пропускать его к Sol без переформулирования. Агент, который вместо challenge сдал патч, получает отказ результата независимо от качества патча.

## 5. Волны и основные задания

Порядок не переставляется. Волна не начинается, пока предыдущая не прошла гейт, **кроме** явно помеченных параллельных.

---

### W0 — Гейт честности

**Зачем:** пока нельзя отличить сделанное от несделанного и увидеть это автоматически, любая работа swarm умножает мусор. Это блокирующая волна.
**Кто:** Sol пишет контракт, Luna-A исполняет, 1 Ox на механику. Внешний swarm **не запускается**.
**Параллельно:** W1 (read-only, не конфликтует).

| WorkItem | Содержание | Якорь |
|---|---|---|
| `W0-01` | Контракт `Unimplemented`: снять `todo = "warn"` (`Cargo.toml:325`); ввести обязательную форму `todo!("<якорь>: <что>")`; завести `docs/UNIMPLEMENTED.md` как генерируемый реестр; ввести отдельный типизированный вариант ошибки `Unimplemented`, отличный от `Unavailable` | `A0.8`, `I0.13` |
| `W0-02` | Закрыть 26 clippy-находок **двумя разными способами, не смешивая**: (а) 8 в `eliot-platform-windows` — следствие того, что крейт переопределяет `[lints]` целиком и теряет workspace-овский `missing_errors_doc = "allow"`; починка — вернуть `[lints] workspace = true` и добавлять исключения точечно. ### 5.1. Отдельно: четыре композиционных корня, у которых нет пути успеха

Это не «недонастроено». Это `main()`, который **по построению** не может выполнить свою работу. Проверено на HEAD:

| Корень | Что происходит | Следствие |
|---|---|---|
| `bins/eliot-agent-bridge` | `kernel_ports()` (`lib.rs:451-460`) делает `KernelClient::load()`, затем `probe()`, затем **безусловный `Err(KernelAdmissionRequired)`**. Вызывается в `main()` **до** входа в цикл stdin → выход с кодом 69. Runner в любом случае строится с `ProviderReadiness::unprobed()` | Единственный агентный ingress не может дойти до `Attach` |
| `bins/eliot-dreamer` | `match connect() { Ok(_) => Err(KernelAdmissionRequired), Err(e) => e }` → выход 78. **Ветка успеха тоже возвращает ошибку** | `A9` не производится ничем |
| `bins/eliot-doctor` | 17 строк: безусловный выход 78 с комментарием *«The current Kernel does not advertise the Doctor operation»* | Цепь recovery не имеет исполнителя |
| `bins/eliotd` | `run_loop` (`main.rs:158-172`) — это `tokio::select!` из `ctrl_c()` и `sleep(5s) → health()`. Больше ничего | Демон, объявленный владельцем задач, admission записи и Context Compiler, не имеет входа для работы |

И замыкающий факт: `commit_canonical(` встречается в workspace **ровно один раз** — как собственное определение в `eliot-governor/src/composition.rs:1292`. **Ноль вызывающих.** Канонический путь записи не вызывается ниоткуда.

Строки `eliot.agent-bridge.activate` и `eliot.agent-bridge.forward-frame` встречаются только в клиентской части самого моста (`bins/eliot-agent-bridge/src/lib.rs:195,270`). Серверных обработчиков в Kernel поиск не находит.

**Что это меняет в программе.** Мой Pulse #1 (W2) идёт через `dogfood` на контуре A и поэтому достижим быстро — это остаётся правильным первым шагом. Но он **не** доказывает D1-ingress архитектуры. Поэтому:

- W2 остаётся как есть: первый наблюдаемый Pulse, дёшево и быстро;
- **порядок провайдеров** для нового контура фиксируется здесь и соблюдается в W4 (см. ниже);
- решение о cutover между контурами **поднимается из W4 в отдельный гейт перед W3** — потому что резать монолиты, не зная, какой контур выживает, значит резать дважды.

**Порядок провайдеров (`R13`), нарушать нельзя:**

```text
1. серверная операция Kernel eliot.agent-bridge.activate;
2. точный ответ Session/WorkScope/Task/fence;
3. маршрут forward-frame/event;
4. входной маршрут submission в eliotd;
5. один вызывающий канонического перехода (commit_canonical);
6. один маршрут read → context → verify → finish.
```

Ни один consumer из этого списка не берётся в работу раньше своего провайдера. Именно обратный порядок произвёл `A-01/A-03/A-05`: consumer требовал `DispatchPermit`, которого провайдер не выдавал, воркер делал локальный суррогат, гейт отклонял authority laundering.

### 5.2. Гейт cutover (между W1 и W3)

Единственное решение, которое Sol обязан принять до разрезания монолитов. Вариантов ровно три:

```text
A. контур A (eliot-app/engine/store) — донор за новыми D1-контрактами;
B. cutover на новый контур с точным адаптером;
C. ретайрмент части legacy после доказанного parity.
```

Четвёртый вариант — продолжать обе линии как равноправные продукты — **запрещён**. Это то, что происходило до сих пор, и это источник дублирующихся типов, двух владельцев `write_receipt` и недостижимых «правильных» реализаций.

Вход для решения: `W1-05` (карта рёбер) и `W1-07` (реестр корней без пути успеха). Решение записывается как `Recoverable Deviation`-совместимая запись с owner, rollback и условием пересмотра.

## 6. Гейты волн

Волна закрывается только так:

```text
1. Luna-A предъявляет: все WorkItem волны в состоянии completed или явно снятые с обоснованием;
2. Luna-A прогоняет DoD-команды волны и кладёт вывод дословно в swarm/gates/<wave>.md;
3. Luna-C НЕЗАВИСИМО прогоняет те же команды и пытается опровергнуть DoD;
4. расхождение между 2 и 3 → волна не закрыта, открывается Mechanism Review;
5. Sol объявляет гейт пройденным и замораживает contract revision следующей волны.
```

Никакой гейт не закрывается отчётом. Никакой гейт не закрывается количеством ACCEPT от агентов — `A16.2` называет это анти-паттерном прямо.

## 7. Матрица назначения

Это **не** мои предположения о моделях. Это правило маршрутизации, измеренное на этом же проекте и записанное в `reports/audit/ELIOT_MODEL_EFFICIENCY_20260814.md` по итогам 82 сессий, из которых 74 содержательные.

### 7.1. Что измерено про каждый класс

| Класс | Сильная сторона (наблюдалась) | Систематический провал (наблюдался) |
|---|---|---|
| **Native Sol** | authority, lifecycle, persistence, runtime-семантика; финальные независимые гейты. Находил дефекты, пережившие зелёные package-тесты: `G-03` (canonical TaskContract из непроверенного proposal), `G-10` (незакрытая saga, proofless readiness), `A-01/A-03/A-05` (исполнение без `DispatchPermit`), `P-11` (утечка registry при pre-poll abort) | дорог |
| **Native Luna** | ограниченный обзор исходников, Cargo-гейты, точечные негативные тесты, первый проход аудита. Отклонила `G-08` вопреки 6/6, `Q-01` вопреки 8/8, `A-10` вопреки 6/6 | **не является финальным authority-гейтом**: её же починка `A-10` до 11/11 всё ещё содержала caller-fabricable signer/session/receipt authority, что нашёл Sol |
| **OpenCode Go Luna** | быстрое производство изолированных кандидатов, тестов и обычных state machine. Дала рабочие каркасы для `G-03`, `G-10`, `P-02`, `P-05`, `P-06`, `P-11`, `S-03`, `S-04`, `A-10`, `A-12`, `A-13` | package-локальные зелёные тесты **скрывали authority-критичные дыры**; sealed Cargo-граф пропускался, **если точные рёбра не были написаны прямо в промпте**; lifecycle/persistence/proof/readiness регулярно неполны; два длинных запуска зависли до полезной работы |
| **DeepSeek V4 Flash** (класс Antigravity/дешёвый скан) | точная механическая инвентаризация, нормализация манифестов, простые ограниченные правки | **не должен владеть** семантическими контрактами, решениями authority, восстановлением персистентности и утверждениями о приёмке |

### 7.2. Правило маршрутизации

```text
1. механическая инвентаризация и манифесты      → дешёвый скан-класс (Antigravity);
2. ограниченный кандидат реализации             → Ox OpenCode Go или Luna;
3. первый проход аудита и точечная починка      → native Luna;
4. authority / runtime / persistence + финальный независимый гейт → native Sol;
5. package-тесты доказывают только поведение компиляции;
   интеграция в корень и семантическая приёмка остаются отдельными.
```

### 7.3. Что из этого следует для брифов

Два следствия переносятся прямо в форму задания и **не обсуждаются**:

- **Ox OpenCode Go получает бриф только с явным списком прямых зависимостей.** Измерено: без точных рёбер в промпте он их пропускает. Поле `one_hop_providers_and_consumers` для этого класса — не формальность, а условие годности результата.
- **Authority-чувствительный результат Ox никогда не интегрируется без native-обзора.** Luna-B не имеет права передать такой результат Luna-A, минуя обзор.

### 7.4. Итоговое назначение по классам работы

| Класс работы | Кому | Почему |
|---|---|---|
| Решение, контракт, разрешение конфликта, финальный гейт | Sol | измеренная сильная сторона + единственный владелец authority |
| Интеграция, Edge proof, Product Pulse | Luna-A | `I2.17`: worker не интегрирует себя |
| Раздача, надзор, приём, отбраковка | Luna-B | дешевле Sol в 10×, задача механическая |
| Независимая проверка гейта | Luna-C | независимость обязана быть реальной |
| Первый проход аудита, точечная починка | native Luna | измерено: продуктивна, но не финальный гейт |
| Механический детерминированный split, генераторы | Ox OpenCode | границы известны, решений не требуется |
| Массовый read-only скан, карты, капсулы, манифесты | Antigravity | дёшево, быстро, без записи и без семантики |
| Фальсификация и challenge | Ox OpenRouter | другой failure domain, другой провайдер |
| **Работа с монолитом > 100k STU** | **никому** | пока не разрезан — это `ContractChallenge`, не задание |
| **Cross-owner authority seam** | **только Sol** | измеренный failure profile дешёвых воркеров совпадает с самым опасным классом дефектов |

Последние две строки — главные. Первую нарушали, разрешая работу по 450k-STU файлу. Вторую нарушали, отдавая authority-швы дешёвым воркерам: именно на этом совпадении «где ошибается дешёвый воркер» и «что в ELIOT несущее» построен весь провал предыдущей кампании.
