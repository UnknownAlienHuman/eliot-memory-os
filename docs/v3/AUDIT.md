# Eliot Memory OS V3 — итоговое заключение для переписывания

**22 октября 2026. Назначение: законченный проектный разбор доступных материалов и задание на новую Architecture / Implementation. Не отчёт о работающем V3 и не заявление, что прочитан весь архив.**

## Вывод

Переписывать нужно не V2 с укороченными именами, а связанный продукт: реальные события сохраняются; нужные знания находятся и раскрываются; Dreamer действительно интерпретирует материал; его результат используется следующей работой; ошибки меняют соответствующее знание или способ обработки. Сложность V2 выросла прежде всего из обязательной управляющей инфраструктуры вокруг этих операций, несоединённых производителей и потребителей, дублирующих состояний и подмены выполненной работы формально правильным объектом.

Моя работа над V3 частично повторила этот дефект: разбор частных ошибок рос быстрее законченного плана, общие слова «обычная память» и «существующий worker» скрывали недоопределённые переходы, а осторожность превращалась в запрет полезной работы. Ниже эти места заменены конкретными проектными решениями. Они **выбраны для переписывания**, а не выданы за реализованные возможности старого кода.

**Результат этого аудита:** сохранить полный смысл Smart Memory OS; убрать ненужных владельцев, разрешительные стадии и повторные вычисления; построить один путь данных с явными потребителями. Переписывание документации можно вести по этому заключению, не начиная новый бесконечный каталог доноров. Недоступные источники и непроверенные реализации перечислены отдельно; они не считаются прочитанными.

### Граница источников

Основание — V1 Canonical Master, выбранные части Understanding Layer и нормативов V2, разобранные связанные пути V2, приложенный Claude revision 4, исторические аудиты и конкретные донорские функции. Полные первичные разборы до этого заключения сохранены в [аудите 0.23](https://github.com/UnknownAlienHuman/eliot-memory-os/blob/41c2291f3b968ddbb2690b2f4be79e1677730de7/docs/v3/AUDIT.md); он остаётся источником подробных координат, контрпримеров и границ каждого вывода. Это не повторное выполнение прежних проб.

В этой редакции получены и сверены полные тексты `ELIOT_AUDIT_2026-10-08_v9(1).md`, `ELIOT-Swarm-AUDIT-2026-10-06(2).md`, августовского аудита относительно Architecture и перечня LLM-проблем. У v9 разобраны **T01–T37**, включая ранее не полученный хвост. Прочитать отчёт не означает заново воспроизвести все его утверждения на текущем коде. Исторические цифры и дефекты сохраняют дату и область источника.

**Исключения:** содержимое ZIP релиза `audit-2026-10-16-incomplete` и полный `ELIOT-WORK-SYSTEM-REPORT-2026-10-14.md` получить не удалось. Поэтому исчерпывающий аудит всего когда-либо перечисленного корпуса не закрыт. Это ограничение доказательной базы, а не новый запрет на переписывание уже определённого продукта.

## 1. Корневые ошибки и что с ними делать

| Частичная работа объявлена полной | Старейшие 512 записей, предел 10000 с отказом, обрезка кандидатов до applicability, потеря связанных оснований после top-k | Адресные индексы, страницы и отбор до packing; неполнота относится к реально просмотренной области |
| Исходы и смысл выводятся из похожести | Token-overlap считает отрицание подтверждением; batch membership становится evidence; повтор источника увеличивает support | Сходство находит кандидатов; условия, реальные события и независимые попытки учитываются отдельно |
| Дополнительный учёт ломает результат | Delivered до handoff; logging после успешного действия превращает его ответ в общую ошибку; replay всей истории на update | Сохранить известный результат, отдельно описать пробел учёта; current row и необходимая история меняются вместе |
| Старый ремонт или общая неполнота останавливают диагностику | Выбранная `diagnose_self_quality` возвращает Blocked по любой прошлой неудаче той же конфигурации | Не повторять тот же неподкреплённый ремонт; новые симптомы и независимая работа продолжаются |
| Проверка формы становится мерой готовности | Конкретный тест считает локальную функцию «модельным вызовом»; записи реестров используются вместо consumer | Не менять production logic ради ложного ожидания. Проверять впоследствии реальные входы/выходы того же продуктового пути |

Это не доказательство, что **все тесты** вызвали разрастание, что весь V2 не имеет работающих путей или что авторы намеренно обманывали. v9 прямо отзывает часть таких обобщений. Обнаруженные пустые и фиктивные пути достаточно серьёзны сами по себе; усиливать их психологическими объяснениями не нужно.

## 2. Какой продукт сохраняется

Eliot — внешняя память и когнитивная поддержка, а не только RAG. Он сохраняет опыт, продолжает текущую работу, понимает устройство проекта по источникам, учитывает противоречия, помогает предвидеть последствия, извлекает методы, переносит их с условиями и улучшает собственные подключённые способы обработки.

**Границы ответственности выбираются явно:**

| Владелец | Ответственность |
|---|---|
| Пользователь и хост/controller | Цель, разрешённые действия, исполнение внешней задачи и её приёмка |
| Eliot | Исходные наблюдения, редакции знания, восстановление контекста, поиск, интерпретация и память исходов |
| Dreamer | Одна из операций Eliot, исполняемая подходящей моделью через controller; не отдельная власть над продуктом |
| Controller | Реальное выполнение модели/инструментов, provider retries, ссылки на нативные сессии и результаты |
| SurrealDB через private Store | Данные, нативные индексы, отношения и транзакции |
| Внешний Research / структурные / документные инструменты | Добыча и специализированное извлечение; Eliot сохраняет необходимое содержание и адреса источников |
| Малый supervisor вне daemon | Наблюдение за реально принадлежащими ему процессами в активный период |

Это сознательно отличается от исходного канона, соединявшего Memory OS и полный Harness, и от варианта Claude, где память сама вычисляет финиш задачи. Сохраняется честность исхода и связность событий, **не второй независимый владелец задач и приёмки**. Concilium, исследование и самоулучшение остаются функциями, а не отложенными навсегда названиями.

## 4. Единая конструкция и данные

Один Rust package и обычные модули `store`, `memory`, `context`, `learning`, `jobs`, `adapters`, `control`. Названия организуют код, а не заказывают семь серверов, traits или crates. Отдельные библиотеки и процессы появляются при реальной границе поставки, зависимости или отказа.

Выбранное начальное хранение в одной SurrealDB:

| Данные | Назначение и consumer |
|---|---|
| `stream` | Привязка реального источника/сессии/ветки и последовательность поступления; capture и чтение конечной порции |
| `observation` | Событие, occurrence time, received position, task/call/parent, текст/blob/source locator; прямой read и интерпретация |
| `memory` | Рабочая редакция утверждения, метода, continuation или view; ordinary find/open |
| `memory_history` | Предыдущие редакции конкретного item, не второй current store; точный historical open |
| `link` | Версионные основания, альтернативы, зависимости и навигация; адресный lookup и пересмотр |
| `job` | Цель преобразования, конечный вход, method revision, состояние, external request и результат; worker и status |

Это стартовая раскладка, не числовой потолок всех будущих таблиц. Типизированные поля нужны для адресации, фильтра и порядка; входной payload сохраняет настоящие особенности источника. Generic JSON не заменяет доменные значения, но не запрещается ради формального нуля `Value`.

У каждой изменяемой записи один Store writer. Нативные unique indexes и короткая транзакция решают локальные повторы и конкурирующие изменения. Related memory/history/links и завершение job фиксируются вместе. Длинное чтение, модель и подготовка blob — снаружи транзакции. После неизвестного acknowledgement читается прежняя identity: новая оплаченная интерпретация не является способом узнать, сохранился ли старый результат.

`find` использует индексированные primary records; точный `open(id, revision)` не ждёт поисковой проекции. Большая выдача имеет страницы. Вектор — производный от конкретного текста и encoder; он не новая смысловая редакция и не причина запускать reflection. Exact/lexical работают до получения embeddings. Совместимость размеров векторов не означает совместимость encoders.

API-профиль SurrealDB 3.3.4 был выбран в прежнем проходе по документации. Это не установленный binary, не обещание совместимости любого будущего SDK и не выполненная миграция. При реализации фиксируются реальные совместимые зависимости и проверяются конкретные запросы, а не строится ещё один query language.

## 5. Полезные пути: вход, действие, сохранение, следующий consumer

| Путь | Вход и реальная операция | Сохранённый результат → потребитель |
|---|---|---|
| Захват | Host tool/result, сообщение, файл или отчёт источника → capture до толкования | Observation с исходным ID → поиск, episode job, status |
| Продолжение | Известные project/session/task/branch → адресное состояние + новые события | Краткое current-work view → следующий model turn |
| Поиск | Задача/ресурс/вопрос → exact + lexical + совместимые vectors, при нужде relations | Полезный метод/основание/исключение → context; детали через open |
| Интерпретация | Конечная связная часть эпизода + близкие existing lessons → реальный controller request | Create / amend / keep → обычная memory, а не skill registry |
| Прямая поправка | Явное исправление пользователя → тот же addressed write | Новая версия и причина → ближайший подходящий контекст без LLM |
| Понимание проекта | Compact structure + нужные исходники/документы/решения → объяснение | Area/question view → orientation и решение об изменении |
| Разногласие | Несовместимые утверждения об одном предмете и условиях → прочитать grounds | Альтернативы и различающий шаг → текущий вопрос; остальная работа не ждёт |
| Исследование | Конкретный пробел → локальные источники, затем configured acquisition | Report, sources, coverage и открытые вопросы → memory/context |
| Перенос | Урок с условиями → reusable owner-scope method, а не копия raw проекта | Общий метод → другой проект через тот же поиск |
| Самоизменение | Наблюдаемый дефект + действующий метод → адресная поправка | Method/config revision → реальный prompt builder или функция |
| Предвосхищение | Срок/план/ожидаемый эффект → условный совет о следующей ситуации | Открытое обязательство/прогноз → подходящая задача; истечение срока не success |
| Забывание | Повторяемый шум, refutation или explicit erase → соответствующая операция | Меньше показа / новая позиция / controlled deletion → обычный read |
| Восстановление | Restart или выбранный backup → primary data, затем derived work | Доступные данные и ясные gaps → пользователь; effects отдельно |

Список не означает модельный вызов на каждом шаге. Разбиение, точные адреса, grouping, native queries и упаковка — обычный код. Смысловая интерпретация вызывается тогда, когда нужен новый смысл. Пустой успешный вывод «не менять» сохраняет существующее; неразобранный ответ, отсутствие source bytes и сбой провайдера не маскируются под no-change.

## 6. Продолжение, методы и перенос: закрытие пробелов 0.24

### Продолжение выбирается адресом, не похожестью

Сначала читается текущая работа по идентификаторам хоста. Continuation содержит цель, выбранный план и причину, реально завершённое, приостановленные/отвергнутые варианты и незакрытые действия. Затем добавляются события после её сохранённого диапазона и явные поправки пользователя. Только после этого ищутся похожие случаи.

Сводка — производное представление, не второй Task owner. Переход на другую ветку выбирает её контекст; семантически похожий отменённый план не становится текущим. При отсутствующей ассоциации событие остаётся в известной сессии, а не относится к «последней задаче» другого агента. Пользовательские ветки не объединяются из-за одинакового текста.

### Изменённый метод должен реально исполняться

Задание сохраняет `(method_id, revision)`; построитель запроса открывает именно этот текст и использует его вместе с конечным входом. Изменение активной редакции действует на новые задания; запущенное не меняется посередине сравнения. Встроенные начальные методы поставляются как нормальное содержимое, а не как неизменная скрытая константа рядом с неиспользуемой записью в БД.

Подключаемые предметы адаптации: текст интерпретации, вопрос и способ синтеза view, формат полезного контекста, поддержанные веса/лимиты retrieval и batching. Для каждого параметра в Implementation указывается функция, которая его читает. Новую SQL-логику, host capability или binary поведение нельзя «реализовать» новой заметкой; это обычная задача разработки. Не требуется компилятор произвольных model policies.

Вклад результата адресуется actual attempt и method revision. Offered, observed-used и unknown-use различаются. Показ нескольких методов не даёт права присвоить общий reward каждому или первому. Повтор одного источника не создаёт независимого успеха. MemP демонстрирует полезную связь workflow→prompt→environment→update, но его выбор первого совпадения `index` и feedback только первому методу не переносятся.

### Происхождение и повторное использование — разные области

Raw event остаётся в исходном проекте. Метод хранит origin и отдельную область reuse: конкретный проект либо общая область владельца. Поиск получает текущие разрешённые проекты и общие методы до top-k. Общий совет не превращает названия, версии и прежний PASS чужого проекта в факты о текущем.

Условия и исходные ограничения раскрытия сохраняются. Пользователь может разрешить автоматическое создание общих условных методов; не нужно approval каждого урока или два обязательных успеха до первого применения. Утверждение об эффективности в разных средах требует соответствующих наблюдений, а не одного флага shared.

## 7. Основания вывода, обновления и противоречия

Обычная citation означает «откуда материал», а не формальную логическую зависимость. Для вывода с известной структурой основания выбран следующий минимальный вариант: relation к точной редакции имеет роль и необязательный идентификатор **группы основания**. Обязательные элементы внутри одной группы нужны совместно; несколько полных независимых групп являются альтернативами. Corroborating и navigation links не заменяют обязательную premise. Пустая или неустановленная группа не доказывает вывод.

Это поля существующих links, не новая БД, ATMS, язык доказательств или требование модели формализовать каждую заметку. Там, где структура не установлена, сохраняются реальный input и квалифицированный вывод; изменение существенного входа назначает адресный пересмотр. Автоматическая логика не угадывает AND/OR по количеству оставшихся рёбер.

Изменение исторического проекта не опровергает прежнее наблюдение. Refutation конкретной premise, смена действующего условия и физическое удаление источника имеют разные последствия. В первом случае пересматривается поддержка, во втором — применимость, в третьем — доступность и контролируемые производные. Удалить citation из прежнего текста недостаточно, чтобы синтез вдруг стал обоснованным или открытым для другого маршрута.

Обычный read проверяет адресованные данные и уже известные ограничения; он не ждёт полного обхода происхождения. Изменения ставят существующие jobs для затронутых outputs. Полезные независимые записи остаются доступны. Последний полученный текст не выигрывает автоматически: учитываются предмет, аспект, перспектива, время и настоящая correction/replacement связь. A→B→A может быть новым событием, а не replay старой A.

Concilium реализует разбор вопроса: сохранить существенные альтернативы, открыть их основания, выбрать полезное различающее наблюдение и затем уточнить позицию. Один агент, инструмент или человек может быть достаточен; дополнительные агенты приходят через controller. Ни число голосов, ни несколько пересказов одной статьи не независимые основания.

## 8. Документы, изображения и предметные артефакты

Не-кодовая память остаётся частью полного продукта. Наличие generic `payload` само по себе её не реализует. Выбраны конкретные семейства adapters:

| Источник | Извлечение / адрес | Что сохраняется |
|---|---|---|
| Текст, Markdown, код, журнал | Native UTF-8/декодирование; lines или byte spans; реальная версия файла | Оригинал, encoding и точный диапазон, не только summary |
| PDF/DOCX/PPTX/XLSX | Настроенный внешний Docling converter; структурированный JSON, а не только плоский Markdown | Исходный файл, converter profile, element/table/cell hierarchy; page/bbox/charspan когда доступны |
| Изображение или GUI | Исходные bytes + кадр/область; описание подходящей моделью только при нужде | Оригинал и координаты; описание/OCR — отдельное производное, не оригинал |
| Аудио/видео | Настроенный ASR/media converter; временные сегменты, отдельно кадры | Ссылка на source bytes и timespan; transcript не доказывает увиденное на видео |
| Внешнее исследование | Фактически возвращённые source handles и report | Полученная версия/цитата/coverage; недоступная ссылка не выдуманное содержимое |

Docling выбран как внешний инструмент преобразования, **не вторая memory platform и не встроенный Python backend Rust-сервиса**. Его официальные [форматы](https://docling-project.github.io/docling/usage/supported_formats/), [модель документа](https://docling-project.github.io/docling/concepts/docling_document/) и [CLI](https://docling-project.github.io/docling/reference/cli/) проверены 22.10.2026. Это подтверждает доступные структуры, не качество на файлах пользователя или установку. Audio/video требуют подходящего pipeline и дополнительных зависимостей; не заявляется готовое понимание любого медиа.

`open` принимает типизированный locator: source revision + вид + действительный адрес сегмента. Ошибка извлечения не удаляет оригинал. Отсутствующую координату нельзя придумать; вместо неё возвращается доступный более крупный элемент с обозначенной точностью. Дословные значения таблицы сохраняются отдельно от их интерпретации. Преобразование, индексирование и создание урока — разные purpose существующих jobs, не обязательный тройной вызов модели.

Research владеет большим внешним корпусом. Eliot хранит достаточные фрагменты/артефакты для своей работы и ссылки на остальное; недоступность Research не выключает локальную память. Нужный полный файл может быть явно импортирован, а не молча продублирован целиком после каждого запроса.

## 9. Исполнение, первое включение и восстановление

### Реальные интеграции

Для уже изученного controller `912df90f...` первый Claude-путь: подготовить agent, создать настоящую задачу интерпретации без фиктивного coding acceptance, dispatch, дождаться результата и получить его через поддержанный reader. `native_input_admitted` и `execution_complete: false` не завершают job памяти. `agent.send` и dispatch-only result reader не образуют автоматически совместимую пару; исправление принадлежит тому же controller adapter.

Отдельная batch-embedding операция остаётся **работой реализации controller**, не существующим API. Её минимальная обязанность определена: выбранный encoder и идентифицированные тексты → соответствующие vectors/ошибки элементов, профиль и известная usage. Это не агент, сочиняющий числа, и не Task на каждый vector. При отсутствии маршрута capture/direct/lexical работают; full vector capability нельзя объявить поставленной.

Research adapter имеет один доменный вход: вопрос, область источников, нужный результат и configured предел работы. Выход: статус, полученный report, source locators, examined scope и gaps. Этот shape — **требование к адаптеру Eliot**, не выдуманное имя готового RPC Research. Вначале его выполняет реальная synthesis/research Task controller с уже доступными acquisition tools. Прямой API Research подключается через его фактический опубликованный интерфейс, не чтением чужой БД и не копированием workflow engine.

### Выбранный локальный запуск

Начальная поставка — один executable Eliot и выбранный SurrealDB server binary. `attach`/CLI/relay используют конфигурацию владельца: data directory, project roots, controller endpoint и route references, включённые виды захвата и бюджеты. Нет отдельного установочного продукта, постоянной Windows-службы по умолчанию или автоматического скачивания исполняемых файлов из модельного текста.

Для самостоятельного Windows-профиля выбран малый supervisor mode того же executable: он запускает daemon, daemon — DB, всё дерево относится к одному OS Job Object. Наблюдение находится вне daemon и включено на период реальной работы. Native [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) дают custody/cleanup, не понимание semantic progress. Сначала нормальное завершение и сохранение, затем прекращение оставшихся собственных процессов; controller и чужие процессы в эту группу не включаются.

Один OS single-instance boundary на data directory предотвращает двойной запуск. Локальный IPC использует текущего пользователя и стандартные OS permissions; credentials не выдаются модели. Это реальная граница процесса, не подписи каждой записи. Режим существующего внешнего supervisor допускается только как альтернативный владелец; два управляющих одним деревом не запускаются.

Готовность первичной БД разрешает capture/read. Ни отсутствующая модель, ни ещё не созданная карта не блокируют старт. Активные jobs/наблюдаемые сессии удерживают сервис; в простое сохраняется pending work и процессы завершаются. Запланированная работа без включённого OS wake выполняется при следующем demand start — приложение не обещает тайно работать после своего выключения.

### Данные и эффекты восстанавливаются по-разному

При недоступной БД relay может сохранить одно исходное событие отдельным файлом в ограниченном spool. Это delivery buffer, не семантическая БД. Primary capture и replay используют ту же identity. Неудача сохранения остаётся ошибкой, а не принятым событием.

Backup сохраняет consistent primary export, нужные blobs, конечный spool cutoff и известную историю удалений. Простой write pause допустим и назван честно; полноценный online snapshot не обещается без реализации. Restore в новый каталог применяет известные удаления и делает primary data доступными до embeddings/maps. Утрата auxiliary history обозначается и не запрещает владельцу явно восстановить выбранную копию. Старое внешнее задание могло уже выполниться: его readback/повтор решается отдельно, без автоматического replay эффектов.

## 10. Что брать у доноров

Донорский механизм — не зависимость на весь продукт. Полная таблица D01–D47 и статус источников находятся в карте. Выбранные группы:

| Потребность | Источники механизма | Решение |
|---|---|---|
| Реальный capture и продолжение | claude-mem, OpenHands, Letta | Штатные host events; сохранение до модели; actual call/result boundaries; continuation отдельно от долговременного урока |
| Извлечение и reconciliation | Hy-Memory, Mem0, Hindsight, LangMem | Конечный input, existing related records, create/amend/keep; raw и ошибки разбора не теряются |
| Полезное извлечение | MemMachine, Subcog, MAGMA, Graphiti | Независимые native arms, адресные отношения, episode expansion до packing; no whole-project scans |
| Организация и раскрытие | A-MEM, Nocturne, Hindsight views | Обновлять реально используемое поисковое описание; aliases к одной записи; сохранённый вопрос с источниками |
| Методы и метаобучение | Harness2, MemP, MentisDB | Реальная редакция метода в следующем prompt; contrasts и no-change; version lookup без отдельного store |
| Понимание кода | Настроенный codebase-memory-mcp, native file search | Структура как вход, не готовое объяснение; без встроенного клона parser/SQLite/daemon |
| Не-кодовые источники | Docling / Docling Core | Внешнее преобразование с адресуемой структурой; оригиналы сохраняются |

Не выбираются для начального ядра enterprise policy engines, WASM runtime, workflow engines, вторая semantic DB, отдельный graph server и сторонние memory daemons. Их неполное исследование не скрывается; у выбранной конструкции просто нет потребителя для такого переноса. Исследовательские scores и benchmark-specific verifiers не подтверждают качество Eliot.

Крупные найденные ошибки доноров остаются в историческом аудите: retire-before-insert; сортировка/группировка не по identity; один source как несколько успехов; пустой parse как no-change; index от первого одинакового метода; обновление неиндексируемых metadata; расширение после top-k с последующим обрезанием; input cache без фактической модели; прогноз без reader. Переносить нужно механизм вместе с понятым ограничением, а не добавлять ещё один контролирующий слой к ошибочной реализации.

## 11. Сверка аудитов и сознательные изменения старой доктрины

**Claude revision 4.** Полезны цель, разделение raw/derived, таблица 63 якорей, идея native DB и реальные сторонние инструменты. Не принимаются как требования: фиксированное число crates/строк/MCP tools; обязательный урок на finish; blanket запрет dependencies; supervisor внутри того же failure domain как независимый; любое новое правило только после двух успехов; перенос примера SQL без проверки native semantics; исключение Research из полного scope. Позиция «все якоря закрыты текстом» не равна реализованной способности.

**v9, T01–T37.** Это исторический ремонт V2 с собственными исправлениями прежних выводов. Сохраняются конкретные ошибки форматов, потеря настоящего payload, локальность восстановления, однозначность состояния, caller/readback и реальные terminal outcomes. Не наследуется обязательство достроить старые Kernel custody, role epochs, регистры и acceptance contracts ради закрытия прежних issues. T09 уже описывает снятый blocker: нельзя снова заказывать его реализацию. Полное распределение T01–T37 приведено в карте.

**Аудит роя 06.10.** Сохраняются native session ownership, одна линия записи, различие поставленного и заявленного, реальная доставка steer, ограничение параллельности ресурсами и немедленная публикация ценных результатов. Выводы о fixed test tasks, line ceilings, обязательном live gate каждого микросреза и автоматической оркестрации не становятся новым порядком пользователя. Код продукта строится связанными путями; минимальный Clippy, затем тесты готового продукта — текущая явно выбранная последовательность.

**Аудит 31.08.** Исторические findings проверяются по их снимку; похвала строгости proof machinery не делает её хорошим решением V3. Отсутствие действующего потребителя, неоднозначная authority и typed/string несогласованность — реальные классы проблем. Их нельзя исправлять очередной доказательной оболочкой над неисполненной операцией.

**LLM-проблемы 07.10.** Ложное завершение, непрочитанные инструкции, потерянное продолжение, ненужные повторы, выдуманные tool results и раздувание реализации становятся конкретными требованиями к producer/consumer, источникам и UI результата. Новое полотно инструкций и квитанций не считается автоматизацией этих проблем.

Ни один аудит не доказал, что все дефекты объясняются одной моделью, тестами или намерением агента. Чужие исторические измерения не перемерены. В этой редакции сверены **выводы доступных отчётов и их переносимость**, а не повторно выполнены все старые runtime-эксперименты.

### Порядок продуктовой реализации после документации

1. Native Store: настоящее событие, restart, точный и lexical read той же записи; первичный путь работает без модели.
2. Один реальный host: tool/result capture и контекст перед следующим решением, без синтетических результатов и модельной блокировки hook.
3. Узкий controller inference route без Task/Attempt: Memory сохраняет конечный episode job и exact recipe/input, controller выполняет один `inference.text`, возвращает durable result artifact, а Memory применяет create/revise/no-change и выдаёт урок следующей работе. `inference.embed` реализуется отдельно как per-input batch-vector operation; ни одна из этих функций не подменяется agent task или генерацией чисел.
4. Current continuation, cross-project methods, источники и project understanding; полноценные vectors/relations дополняют тот же read path.
5. Подключённое изменение методов, исследование, разногласия, прогнозы, retention и восстановление завершают полный scope. Нужное независимое наблюдение входит в поставку реально работающего фонового сервиса, а не откладывается ради удобного подсчёта процессов.

Это последовательность работающих возможностей, не пять новых гейтов. Незавершённая функция возвращает свою фактическую ограниченность; соседние функции работают. Поздние тесты обращаются к тем же production entrypoints. Исправлять нужно неверное ожидание или отсутствующее поведение, а не добавлять ветку, которая выдаёт удобный тесту успех.

Не переносить V2 runtime по кускам под новыми названиями. Не поддерживать старые протоколы по умолчанию. При необходимости старые данные импортируются отдельным явным преобразованием, сохраняющим реальный источник и границы; это не обязанность воспроизвести старую ОС.

## 38. One-shot inference without a second task manager or a second provider stack — 1.0

**24 октября 2026. Проверенная база:** Memory OS branch `d97b9bfb`; controller `38db378c559dd0d95cd60db26702ffa73a954258`; Hy-Memory `6b0bd866798049940c752c402512bb0e16c98a2b`. Это архитектурное решение и source trace, не реализованный route и не model run.

### 38.1 Найденная ошибка проекта V3

Предыдущая редакция правильно убрала отдельный `eliot-dreamer.exe`, но для первого `episode_learning` привязала один text request к controller `task.dispatch`. Настоящий caller показал, что это не «вызвать модель», а полный жизненный цикл разработки:

```text
TaskSpec(objective + phase + >=1 requirement)
→ registered Manager/Operator
→ controller-owned Attempt
→ ready native binding
→ immutable first task.dispatch
→ agent.result/artifact read
→ Attempt disposition
```

Claude route дополнительно требует подготовленный executor, первый native input именно через `task.dispatch` и текущую initial-dispatch identity. Эти механизмы нужны для агентной работы с ownership, tools, continuation, review и acceptance. Для операции «проанализировать замороженный эпизод и вернуть typed proposal» они дублируют уже существующий Memory `job` и создают второй task manager.

Временный ответ `d97b9bfb` ушёл в другую крайность: direct OpenAI-compatible client внутри Memory. Это убирало Task/Attempt, но дублировало бы model credentials, provider/model routing, harness/local-model integration, usage accounting и retry/readback рядом с уже выбранным владельцем `eliot-swarm-controller`. Такой дубликат снова породил бы расходящиеся route profiles и два места исправления provider quirks.

### 38.2 Сохранённое требование старой архитектуры

Перечитаны старые I9.1, I9.3 и T12. Их полезный смысл:

- один конечный Dreamer job для конкретного вопроса;
- один допущенный model attempt;
- ограниченный input и структурированный результат;
- отсутствие постоянного LLM-loop;
- model/provider independence;
- реальный последующий consumer.

Не сохраняются старые средства:

- отдельный Dreamer process;
- Dreamer ledger поверх обычной работы;
- Governor bundle/admission/lease chain для внутренней обратимой интерпретации;
- отдельный provider stack;
- обязательная candidate/promotion ceremony.

### 38.3 Выбранная граница

Memory сохраняет узкий интерфейс `TextInferenceClient`, но initial adapter направлен в новый controller one-shot route, а не прямо к provider:

```text
Memory job + exact recipe/source revisions
→ saved TextRequest(request key, route profile, exact prompt, limits)
→ controller inference.text
→ durable controller result artifact
→ retained TextResult in Memory job
→ purpose-specific decoder
→ publish_revision
→ next context
```

Memory владеет job, frozen input, recipe revision, source coverage, decoder и publication. Controller владеет credentials, route/provider/model/harness execution, request deduplication и transport/result readback. Ни один не копирует state другого.

`inference.text` обязан использовать существующие controller Operation/request-replay/artifact primitives, но **не** создавать Task, Requirement, Attempt, workspace, review, submission или acceptance. Параметры — stable `client_request_id`, configured route profile, exact prompt, finite output limit и response format. Public result различает complete, partial, failed и unknown, возвращает effective model/finish/usage/limits и usable artifact handle.

Embeddings получают отдельный `EmbeddingClient`/`inference.embed` с per-input result mapping. Они не становятся Dreamer agent tasks.

### 38.4 Retry и unknown outcome

Hy-Memory полезен как простой configurable OpenAI-compatible request/result adapter: content, model, finish reason, usage и response ID. Его retry-loop — антидонор: timeout/connection/408/429/5xx могут автоматически повторить уже принятый inference без native idempotency/readback.

Для Eliot:

1. exact request сохраняется в Memory job до I/O;
2. controller deduplicates exact caller/request ID/params;
3. потерянный admission reply восстанавливается тем же request;
4. после Operation ID читается Operation/result, а не выполняется новый inference;
5. exact response bytes сохраняются до parse/publication;
6. Store conflict повторяет publication сохранённого ответа;
7. ambiguous transport/provider outcome остаётся `unknown`;
8. новый attempt создаётся только явным решением владельца либо после доказанного non-admission/native idempotent retry.

Empty, malformed, truncated, failed и unknown не превращаются в `changes=[]`/no-change.

### 38.5 Что установлено и что остаётся

В текущем controller method catalog `inference.text` и `inference.embed` отсутствуют. Existing `task.dispatch`/Claude path и его result gaps R-027/R-046 не считаются реализацией нового one-shot route. Нужна adjacent-repository функция у владельца controller.

Нормативные Architecture draft.4, Implementation draft.17, Cognition draft.7 и README теперь согласованы:

- Base не зависит от controller/model;
- first learning требует один narrow controller inference route;
- agent Tasks остаются для настоящей agent work;
- provider stack не дублируется в Memory;
- tests не становятся ранней платформой: сначала connected production code и minimum Clippy, полный suite — после реализации продукта.

**Не выполнено:** controller route, Memory adapter, schema/migrations, model call, Windows/runtime qualification, tests или benchmark. Реестр R-047/R-048/R-049 хранит активное состояние и следующую работу.
