#### 3.3. Точный рабочий маршрут

**Intake.** Authenticated requester → Governor: прочитать разрешённый source/frame input, связать A-03 job и frozen manifest с текущими scope/fence/policy/route/budget → получить реальное T1.8 admission → K0 `JobOperation::Submit` → K2 → K1 → Store named family → Surreal transaction → QUEUED receipt. Kernel не выбирает модель и не толкует содержание job. Поля requester/role/admission в JSON не заменяют фактическую session/capability проверку.

**Claim/start.** Отдельный Kernel launch operation привязывает queued job/attempt/revision к worker artifact/config/protocol/generation и защищённому handoff. Worker получает эту identity после authenticated attach и вызывает `LeaseExact`, затем `Start`. K2 только маршрутизирует и проверяет права; он не запускает процесс внутри Submit/Lease handler. Process launch, job lease и provider start — три разные операции.

**Semantic run.** Governor `ReadApi::state/query/resource` даёт точные canonical views и handles; A-04 `plan_bundle`/`finalize_bundle` использует реальные замеры и disclosure observations. Затем existing Curation prepass → допущенный provider attempt → grounding → A-05 pre-handler validation → `eliot_dreamer_orientation::project_orientation` → intrinsic output checks. Pure `step_dreamer_cycle` управляет соседними фазами; все его owner outcomes происходят от реально вызванных операций. Frame с вопросом не выдумывается из A-03 job: используется существующий Orientation input contract и точный source handle. Declared provenance из ReadApi не повышается до independently verified evidence.

**Model binding.** Использовать `AgentCoordinator::plan`, затем существующее внешнее admission и `AgentCoordinator::new_with_admitted_provider` / `restore_with_admitted_provider`, действительные ProviderExecutionBinding и отдельные logical/physical route receipts. Runtime получает provider result через этот контур. `OpenCodeClient` — существующий adapter, не разрешение Dreamer самостоятельно выполнить read-only bootstrap и объявить полученный `NoAuthorityRunResult` допущенным результатом. Credential/account/runtime collection остаётся у существующих владельцев; pure coordinator не становится I/O executor.

**Output. OWNER DEFAULT (proposed):** сохранить точные result bytes существующим S-04 owner, затем записать immutable result reference в Dreamer ledger и предоставить requester pull через Status + exact governed resource retrieval; это устраняет необходимость отдельной push-очереди и новой delivery authority. Перед BeginVerification создать реальный Checkpoint с result reference, completed/remaining phases, route, budget и possible-effect state. `BeginVerification` и `Publish` проверяют прежнее admission и lease; terminal receipt возвращается только после durable readback. K0 `OpaqueContentRef` требует реального artifact identity, длины и digest; content SHA-256 не подменяется BlobHash с другим алгоритмом.

**Cycle profile. OWNER DEFAULT (proposed):** для Orientation `ExternalAdmission` означает только admission к ограниченной публикации результата исходного job, не canonical memory application; bind phase rule к реальной Governor-authorized BeginVerification operation, а `ClosureObserved` — к реальной PublishOutcome receipt и readback. Это конкретная предлагаемая привязка existing `PhasePolicyRule`, не существующий готовый adapter и не фиктивная «проверка прошла». Нельзя трактовать Store acknowledgment как Task Finish. CaptureObservation/AppendAuditEvent допустимы лишь для своих настоящих observation/audit событий, но не нужны как заменитель job ledger.
